# 文件传输模块：协议和安全

官方模块 `rcsdk.file-transfer`（`modules/file_transfer/`，库 `RemoteControl::FileTransfer`，头文件 `rcsdk/file_transfer.h`，只用 `rcsdk/module.h`）的设计：一次传输怎样进行、线上格式、怎样写文件、断线和续传、安全。怎样用见开发者指南的[文件传输](guide/15-modules.md#文件传输rcsdkfile-transfer)；接口以头文件为准。已实现，包括：`RCS_FILE_DONE` 等存储做完结束要做的事才送出（3.6 的“结束的顺序”）；按安全审查加的等决定的清单的预算（3.2、第 4 节）、独占的临时文件（3.5、3.6）、经打开的目录句柄做收的一端所有的文件操作（3.5）。Mac 和 Windows（MSVC）上的自动化测试通过（单元测试和会话场景：两个方向、目录、冲突、拒绝和超时、暂停和取消、限速、1 GiB、断线重连、跨运行续传、`target = HOST`、经助手链接）；跨机器、无人值守时的实机传输还没有验证（[ROADMAP](ROADMAP.md#当前状态)）。

## 1. 要什么

远程桌面和远程协助几乎都要传文件：观看端把安装包、日志发给对方，或者从对方机器上取文件。SDK 负责可靠、加密、不抢画面带宽地把文件送到；**放在哪里、要不要收、界面长什么样，由宿主决定**。

不做：浏览对方的文件系统（那是宿主的界面加上它自己的消息），复制粘贴文件（建在这个模块上，由剪贴板模块做，见第 8 节）。

## 2. 现有的基础

- 模块的可靠消息：走会话的加密连接，完整、按序到达，单条最多 1 GiB，每个对端一个队列，放不下是 `QUEUE_FULL`，有空间时 `room` 回调；和数据通道一样排在输入之后、让路给画面（UDP 上有自己的拥塞窗口，只用视频剩下的带宽）。
- 模块的机器那一半：分享端在助手里（无人值守时是用户会话里的进程），观看端在它自己的进程里。剪贴板就是这样读写系统的。

## 3. 设计

### 3.1 谁读写文件

**机器那一半读写文件**（`target = SYSTEM`，默认）。无人值守时会话在服务（SYSTEM）里，文件应该在用户的会话、用户的账户下读写，正好是助手所在的地方；会话那一半只管和对端的协议。数据流：发送端的机器那一半读 → 会话那一半 → 网络 → 对端的会话那一半 → 对端的机器那一半写。机器那一半在自己的线程上一个一个地做（列目录、读、写、改名），慢的磁盘不会挡住模块的调用。

另一种来源是宿主自己（`target = HOST`，和剪贴板一样）：宿主用回调给出字节、收下字节，适合文件在宿主自己的存储里（沙盒、数据库、内存）的情况，这时机器那一半不碰文件系统。宿主的回调在会话那一半自己的一个线程上调用，一次一个，按每个条目的顺序。

### 3.2 一次传输

一次传输是一组条目（文件和目录，带相对路径），发送端先发**清单**（每项的相对路径、种类、大小、修改时间，合计大小和条目数），接收端的宿主决定收不收、收到哪里，然后才开始发内容。

```c
/* 设置（rcs_module_config.settings） */
typedef struct rcs_file_transfer_settings {
    uint32_t struct_size;
    rcs_file_flow flow;            /* RCS_FILE_SEND | RCS_FILE_RECEIVE：本端允许的方向；默认 0：都不允许 */
    rcs_file_target target;        /* SYSTEM（机器那一半读写文件，默认）或 HOST（宿主的回调） */
    uint32_t max_items;            /* 一次传输最多几项，两个方向都按它：1～100 000，默认 10 000 */
    uint64_t max_offer_bytes;      /* 一次传输最多多大，0（默认）不限 */
    /* 等本端宿主决定的清单（OFFERED）的预算，超过就立即拒绝（BUSY），宿主看不到 */
    uint32_t max_pending_offers;      /* 来自一个对端的：1～10 000，默认 100 */
    uint32_t max_pending_items;       /* 来自一个对端的条目合计：max_items～1 000 000，默认 20 000 */
    uint32_t max_pending_items_total; /* 所有对端的条目合计：max_items～1 000 000，默认 100 000 */
    uint32_t offer_timeout_ms;     /* 本端宿主多久不决定就算拒绝：1 000～3 600 000，默认 120 000 */
    uint32_t reconnect_wait_ms;    /* 对端（或分享端的助手）断开后传输等它回来多久：0～3 600 000，默认 60 000 */
    uint64_t max_bytes_per_second; /* 本端发的每次传输最多多快，0（默认）不限 */
    uint32_t keep_partial;         /* 收、SYSTEM：1（默认）连接或运行结束时留下写了一半的文件，供下次续传；0 删掉 */
    /* target HOST：read（发）、write（收）、resume（收，可以 NULL）回调和 user_data */
} rcs_file_transfer_settings;

/* 发：条目是本机的绝对路径（SYSTEM，目录连同里面的一切）或宿主自己的名字、种类、大小、时间（HOST）。
   resume_token 全 0 是新的传输，否则是以前一次传输的令牌（续传）。返回传输编号。 */
rcs_result rcs_file_send(rcs_session session, const rcs_file_offer* offer, uint64_t* out_transfer);
/* 收：对方的清单到了（事件 RCS_FILE_OFFER），宿主决定。HOST 时 directory 为 NULL。 */
rcs_result rcs_file_accept(rcs_session session, uint64_t transfer, const char* directory,
                           rcs_file_conflict on_conflict);
rcs_result rcs_file_reject(rcs_session session, uint64_t transfer, const char* reason);
/* 两端都能取消；暂停和继续（任一端暂停就停）。 */
rcs_result rcs_file_cancel(rcs_session session, uint64_t transfer);
rcs_result rcs_file_pause(rcs_session session, uint64_t transfer, uint32_t paused);
/* 一次传输现在怎样：状态、令牌、字节、速度、结果和原因；条目从 first 起分页取。 */
rcs_result rcs_file_get_transfer(rcs_session session, uint64_t transfer, rcs_file_transfer_info* out);
rcs_result rcs_file_get_items(rcs_session session, uint64_t transfer, uint32_t first, rcs_file_item_info* items,
                              uint32_t item_size, uint32_t capacity, uint32_t* out_count);
/* 对端允许什么（它的问候）；删掉以前留下的续传文件。 */
rcs_result rcs_file_get_peer(rcs_session session, rcs_viewer_id viewer, rcs_file_peer* out);
rcs_result rcs_file_discard(rcs_session session, const char* directory, const uint8_t* token);
```

几点说明：发送的参数收进一个结构体 `rcs_file_offer`（含观看端编号和续传令牌，以后加字段不改函数）；`rcs_file_get_items` 带 `first`，十万项的传输可以分页取；另有 `rcs_file_get_peer` 和 `rcs_file_discard`；速度上限在设置里（`max_bytes_per_second`，运行中改立即生效）。

决定用函数，不用回调：宿主可以先弹窗问用户，什么时候决定都行（和异步准入同一个思路，见[指南 07](guide/07-sharing.md#准入先问用户再放行)）。不决定就按 `offer_timeout_ms` 拒绝（`TIMEOUT`）。函数也可以在 `on_event` 里直接调：它们引起的事件在那次 `on_event` 返回后送出（核心的规则，见 3.7）。

`rcs_file_send` 立即返回：SYSTEM 时机器那一半先列出条目（`RCS_FILE_PREPARING`），列不出来（路径不存在、名字对端放不下、超过限制）就以 `RCS_FILE_DONE` 结束并写明原因。参数不合法是 `INVALID_ARGUMENT`；本端没有 `SEND`、对端没有 `RECEIVE`、没连上、SYSTEM 时机器那一半没在运行是 `INVALID_STATE`，原因写明是哪一个（对端允许什么在它的问候里）。

### 3.3 事件（`RCS_EVENT_MODULE`，模块自己的 `kind`）

| kind | 什么时候 | payload |
| --- | --- | --- |
| `RCS_FILE_OFFER` | 对方发来清单，等本端宿主决定 | `rcs_file_offer_event`：传输编号、条目数、合计大小、是不是续传、令牌 |
| `RCS_FILE_PROGRESS` | 进行中，每 250 ms 最多一次 | `rcs_file_progress_event`：完成的字节（续传和跳过的算在内）、当前条目、完成的条目数、最近一秒的速度 |
| `RCS_FILE_ITEM_DONE` | 一个条目完成、跳过或失败 | `rcs_file_item_event`：条目序号、状态、结果、原因 |
| `RCS_FILE_DONE` | 整次传输结束，模块对它要做的事也做完了（见 3.6 的“结束的顺序”） | `rcs_file_done_event`：怎么结束（完成、对方拒绝、取消、失败）、是不是对端结束的、结果、原因、各种条目数、是否留下了续传文件 |
| `RCS_FILE_STATE` | 状态变了：准备中、等决定、进行中、暂停（哪一端）、等对端回来 | `rcs_file_state_event` |
| `RCS_FILE_PEER` | 对端允许什么变了（连上时、它改了设置时） | `rcs_file_peer` |
| `RCS_FILE_DISCARDED` | `rcs_file_discard` 做完了 | `rcs_file_discard_event`：令牌、结果、删了几个文件 |

事件的 `viewer_id` 是传输的观看端（观看端那边是 0）。

### 3.4 线上（模块消息，小端序）

问候 29 字节：本端允许的方向、本次运行的随机编号（16 字节，同一次运行里重连回来的同一端说同一个）、`max_items`、`max_offer_bytes`。

每条消息都用**发送方**给传输的编号（`rcs_file_send` 返回的那个，或者它给一次取的编号）指明是哪次传输；`CANCEL`、`PAUSE` 两端都会发，带标志说编号是谁的。一次取在它的 `OFFER` 到达之前用取的一方的编号（`FETCH`，和这时两个方向的 `CANCEL`）。

发布和取（剪贴板粘贴文件靠它们）用到的：`FETCH`（取的一方：它的编号、发布编号、`INTO` / `READ`）；`OFFER` 带一个标志和“应哪次取”（取的一方的编号、方式）：`INTO` 到达时直接接受（目录是取时给的），`READ` 发出就开始、没有 `ANSWER`；`READ`（取的一方：读编号、条目、偏移、1 B～256 KiB）和 `DATA`（发送方：读编号、结果、全部字节或原因），没回答的读合计不超过 16 MiB，超过是违反规则；`CANCEL` 的“谁的编号”有两位（发送方的、取的一方的编号）。发布不上线：只有编号随宿主（或剪贴板模块）的消息到对端。源头读文件经目录句柄：清单给每项条目一个“基准目录”（目录条目本身、文件条目所在的目录），读时从它一段一段打开，中间被换成链接的目录不跟随（见 3.5）。

两半之间也有消息，两半和两端都须同一版本：准备的请求带一个“续传”标志（接收端宿主看到的 `resuming`，见 3.6），读的请求带条目在线上的路径（机器那一半的回答里只用它称呼文件，见 3.5）。

| 消息 | 谁发 | 内容 |
| --- | --- | --- |
| `OFFER` | 发送方 | 编号、标志（重发、续传、发送方暂停着）、令牌、“结果已知到第几项”、条目清单（种类、大小、修改时间、相对路径） |
| `ANSWER` | 接收方 | 接受；纪元（epoch）、接收方暂停着、从哪里发起：某项之前都不用发，之后的项各自从哪个偏移开始，或者不用发（已完成、跳过、失败，结果另有 `ITEM_DONE`） |
| `CHUNK` | 发送方 | 纪元、条目序号、偏移、数据（最多 256 KiB） |
| `ITEM_END` | 发送方 | 纪元、条目序号、结果（全部发完，或读不了和原因） |
| `ACK` | 接收方 | 条目序号、已经写好的字节数 |
| `ITEM_DONE` | 接收方 | 条目序号、完成 / 跳过 / 失败、结果、原因、是不是以前的运行完成的 |
| `CANCEL` | 两端 | 结束：拒绝、取消或失败，结果和原因 |
| `PAUSE` | 两端 | 暂停或继续 |

- **流量**：每次传输“读出来、排着队、在路上、对方还没写好”的字节加起来最多 4 MiB（每块读之前算进去，对方的 `ACK` 说写好了才减掉），所以大文件不占内存，接收端写得慢时发送端自然慢下来。对端怎么发都一样（安全评估 SA-11）：一端交给自己存储（机器那一半或宿主的回调）的读、写，在存储回答之前一直算数。发送方收到 `ANSWER` 时不清掉已经交给存储、还没读回来的块，而是标成“不发”，等它们回来；接收方记着交给存储、还没写好的每一块（存储按顺序回答），重发的 `OFFER` 不把这个数清零：它先把纪元加一，等存储写完手里的再回 `ANSWER`，这之前到的块和条目结束都丢掉；一块会让没写好的超过窗口加一块时，也不算违反规则，而是丢掉它、照样等存储写完再回 `ANSWER`（正常的发送方在某一项失败后可能已经接着发下一项，那一项的块还在写）。不这样算的话，已经接入的对端反复重发 `OFFER`（接收方）或 `ANSWER`（发送方），每次都让窗口从头算，慢盘前排着的写或读可以涨到整个传输的大小：测试 `file_transfer.flow` 里 8 次重发，不这样算时接收方的存储排了 34 MiB、发送方的排了 128 个读，这样算是 4.25 MiB、16 个。每个对端的模块队列（最多 16 MiB，装得下最大的清单）满了就是 `QUEUE_FULL`：之后的消息按顺序排在模块自己的等待队列里，`room` 回调时再发。模块队列和宿主的数据、别的模块轮流发，大文件不会挡住它们。
- **顺序**：条目一项一项按清单的顺序发，每项的块按偏移发，最后是它的 `ITEM_END`。接收方只收“正在等的那一项、正好接着的偏移”的块；别的都是违反规则（`PROTOCOL`，传输失败），只有旧纪元的块、新纪元的 `ANSWER` 发出之前的块、超过窗口的块和已经结束的条目的块是静默丢掉的（见上一条和 3.6）。`READ` 方式的取收到 `ANSWER` 是违反规则（它没有 `ANSWER`）。
- 每块的完整性由会话的加密连接保证（每条记录都认证），不另算校验和。
- 对端发来的一切都检查：路径（见 3.5）、种类和大小（目录和“其他”大小为 0，合计不溢出）、条目数、同一路径两次、结果码、文字是 UTF-8、长度、没有多余的字节。机器那一半和会话那一半之间的消息也同样检查（另一个进程里的助手也可能被攻破）。

### 3.5 写到哪里、怎么写

- 路径只接受相对路径，规则在两端都一样，在哪个系统上都落在宿主给的目录下面：UTF-8，`/` 分隔，最多 1023 字节；每段 1～255 字节，不是 `.` 或 `..`，不是 Windows 的保留名（`CON`、`PRN`、`AUX`、`NUL`、`COM0`～`COM9`、`LPT0`～`LPT9`、上标 1～3 的 `COM`/`LPT`、`CONIN$`、`CONOUT$`，带不带扩展名、不分大小写），没有控制字符和 `\ : * ? " < > |`，不以点或空格结尾，不以 `.rcsdk-part` 结尾、不以 `.rcsdk-resume-` 开头。所以绝对路径、盘符、UNC 路径都进不来。发送端列目录时遇到放不下的名字，整次传输以 `INVALID_ARGUMENT` 结束并写明是哪个文件，不悄悄改名。
- 先写进同目录的临时文件（`名字.<令牌的 32 位十六进制>.rcsdk-part`），写完设好修改时间，再改成它的名字；取消或失败时删掉临时文件（连接或运行结束、并且要续传的除外，见 3.6）。名字带完整的令牌，两次传输同时把同名文件写进同一目录时各写各的（只带令牌的一部分的话，宿主自己选的续传令牌那一部分相同时，两次传输写的是同一个文件、内容混在一起还报告成功）。代价是名字长了 44 个字符：名字的最后一段加上它要放得下文件系统对名字的限制（NTFS、APFS 都是 255 个字符），放不下的这一项失败，原因是系统的“名字太长”。
- 临时文件新建时是独占的（POSIX `O_CREAT | O_EXCL | O_NOFOLLOW`，Windows `CREATE_NEW`）：那个名字上已经有任何东西（别人放的文件、符号链接）这一项就失败（`INVALID_STATE`），从不覆盖、从不经它写到别处。这次传输自己的临时文件要接着写时（续传；分享端的助手换了，从已写好的地方或从 0 再写）才重新打开它，打开时先查清楚再截短：不是符号链接（`O_NOFOLLOW`）、不是管道（`O_NONBLOCK`，查完再清掉）、是普通文件、没有别的硬链接、不比已写的短，否则这一项失败。会话那一半告诉机器那一半哪一块是这一项在这次传输里的第一块（两半之间的写请求多了一个标志）。
- 同名文件按宿主选的 `on_conflict`：覆盖（那里是目录时这一项失败）、改名（`名字 (1).扩展名`、`(2)`……第一个空着的；名字太长时截短主名，不截半个字符）、跳过（这一项 `SKIPPED`）、整次失败（`INVALID_STATE`）。开始之前就检查一遍（跳过和整次失败在开始前就定了），写完改名时再按规则处理一遍（中间可能有人放了同名文件）。改名不覆盖用不替换的系统调用（macOS `renamex_np(RENAME_EXCL)`、Windows `MoveFileExW` 不带替换），不会和别的程序抢同一个名字。目录已经存在就往里放（合并），那里是文件时目录这一项失败。
- 接受后、开始前检查目标卷的剩余空间（要写的字节减去续传已有的），不够就整次失败（`DEVICE`），原因写明需要多少、还剩多少。同时在写的传输一起算（安全评估第二轮）：机器那一半记着每次接受的传输还要写多少、在哪个卷上（POSIX 的 `st_dev`，Windows 的卷序列号），写一块减一块，结束（`COMPLETE`、`DISCARD` 结束、`CLOSE`）时去掉；新的传输要的加上同一卷上别的传输还要写的超过剩余空间就失败，原因写明其中多少是别的传输的。只和剩余空间比的话，几次同时接受的传输各自都过得去，合起来写满磁盘后才各自以 `DEVICE` 失败。剩余空间本身留不留余量是宿主的事（`max_offer_bytes`、选哪个卷、丢掉留下的续传文件）。
- **写在收下文件的目录里，不是每次再按路径找**：收的一端的机器那一半对一个请求，先打开宿主给的目录，再一段一段往下开子目录，每一段都相对上一段的句柄打开、不经过链接；建临时文件、写、改名、删除、设时间、建子目录、读和写续传的记录都相对这些句柄做。检查过的目录和用到的目录是同一个，所以另一个能在接收目录树里写的进程（例如以 SYSTEM 跟随安全桌面的助手，收到普通用户也能写的文件夹里）在检查之后把中间的某一段换成符号链接（POSIX）或目录联接（Windows，不需要特权），临时文件和最后的改名也落不到宿主给的目录之外。
  - POSIX：`open(宿主给的目录, O_DIRECTORY)`，往下每一段 `openat(…, O_NOFOLLOW | O_DIRECTORY)`（那里是链接就是 `INVALID_STATE`，不跟随），其余用 `openat`、`mkdirat`、`renameat`（不替换时 macOS `renameatx_np(RENAME_EXCL)`，别处 `linkat` 加 `unlinkat`）、`unlinkat`、`fstatat`、`utimensat(AT_SYMLINK_NOFOLLOW)`。被换走的目录，句柄指的还是原来那个：这一步写进被移走的目录里（不会写到链接后面），下一步按路径再走到那一段时遇到链接，这一项失败（`INVALID_STATE`），写了一半的文件留在被移走的目录里（不能再安全地找到它，日志写明）。
  - Windows：宿主给的目录用 `CreateFileW` 打开（路径上的链接照旧跟随），往下每一段用 `NtCreateFile` 带 `RootDirectory`、`FILE_OPEN_REPARSE_POINT` 相对上一段打开，是符号链接或目录联接（名字代理的重分析点）就这一项失败（`INVALID_STATE`）；每一段的句柄都开着、不共享删除（没有 `FILE_SHARE_DELETE`），并且持有上一段的句柄直到这次请求结束：这些目录在用的时候不能被改名或删除，也就换不成联接。文件相对目录句柄建（`NtCreateFile`，`FILE_CREATE`），改名用 `NtSetInformationFile(FileRenameInformation)` 带 `RootDirectory`（`SetFileInformationByHandle` 的 `FileRenameInfo` 不接受，返回参数错误），删除和设时间也是先相对打开再对句柄做。相对打开只请求了写的句柄，之后查属性被拒绝访问（Windows 上的测试发现），所以每次打开都自己加上 `FILE_READ_ATTRIBUTES`。
  - 边界：保护的是宿主给的目录**下面**的树。宿主给的路径本身每次请求照旧解析，路径上的链接被跟随（那是宿主的选择；macOS 的 `/tmp` 就是链接）；能改宿主给的目录的上一级、把目录本身换成链接的进程，等于改了宿主的选择，不在这里防。每个请求（不是每一块）重新打开这些目录；一次传输之间目录被换掉，下一个请求按新的路径走，遇到链接就失败。
  - 按路径做的问题：对路径的每一段只 `lstat` 一次，之后的 `open`（`O_NOFOLLOW` 只管最后一段）、`mkdir`、`rename`、`unlink`、`utimensat` 又从头解析整条路径的话，检查和使用之间被换成链接，临时文件和改名就落到外面。测试 `file_transfer.store` 的 `swapped`（测试接缝 `Store::checked` 在检查之后、使用之前停住，把那一段换成链接）检查的就是这种情况。
- 发送端读源文件：列出之后源文件被换成管道（FIFO）时，不带 `O_NONBLOCK` 的 `open` 会让机器那一半的线程等写端等到永远，这个线程是一个一个处理所有请求的，整个模块的磁盘工作都会停。所以带 `O_NONBLOCK` 打开（管道马上打开成功），确认是普通文件再清掉 `O_NONBLOCK`；不是普通文件（管道、设备）这一项以 `INVALID_STATE` 失败。读源文件经条目的基准目录一段一段打开，中间的链接不跟随（3.4；按路径打开、只查最后一段的话，路径中间的目录被换掉时读到的可能是别处的文件）。
- 符号链接不跟随：发送端列出它（种类 `RCS_FILE_OTHER`，Windows 上是符号链接和目录联接；云盘占位文件照常当文件），两端都记为跳过（`UNSUPPORTED`），内容不发；接收端路径上有符号链接（Windows 上还有目录联接）挡着就这一项失败（接受时就发现的，在接受时失败，不等到写第一块），临时文件的位置上有符号链接时这一项失败（接受传输时那里的东西是以前的运行留下的、这一项要从头写的，删掉链接本身），从不写到链接指向的地方。
- 修改时间保留（文件写完时设，目录在整次完成时由深到浅设），权限和扩展属性不传（跨系统没有对应）。新建的文件和目录拿这个进程新建任何东西时拿的权限：macOS、Android 上是 `0666` / `0777` 去掉进程的 umask，Windows 上继承所在目录的访问控制，和任何程序存文件一样；临时文件和记录也一样。能在接收目录里写的其他账户照样能改其中的东西，带粘滞位的目录（`/tmp`、`/Users/Shared`）里也能在一次传输接下来要用的名字上先放自己的文件（续传时临时文件和记录不检查属主：有的卷上看到的属主不是写它的账户，例如 FAT 卷、一些版本的 Android 共享存储，查了就续不上；没有在这些卷上验证，所以不加）：宿主应该收到只有本账户能写的目录里（安全评估第二轮的审阅结论，写进头文件）。
- **原因里不写本机路径（安全评估 SA-16）**：机器那一半的回答（条目的结果、传输结束的原因，`ITEM_DONE`、`ITEM_END`、`CANCEL` 原样发给对端）和日志里，文件一律用它在线上的相对路径称呼：收的一端是接收目录下的路径，宿主的目录本身叫“the receiving directory”；发的一端是条目在线上的名字（宿主给条目改了名时也不露出本机的文件名），列目录时出错的源头用“Entry 序号”和它要用的名字。日志里传输没做完就离开的说明也不写目录和记录的路径（宿主用 `rcs_file_get_transfer` 知道在哪里）。原因里带着绝对路径（`/Users/<用户名>/…`）的话，对端和拿到日志的人都看得到用户名和目录结构。`files.hpp` 的 `Directory` 只记“消息里怎么称呼”，打开它的人给出顶层的称呼。
- 读的时候文件变了（大小或时间和清单里的不同）这一项失败（`INVALID_STATE`），接收端删掉它的临时文件。
- Windows：路径一律转成 `\\?\` 开头的完整宽字符路径，不受 260 字符的限制；剩余空间用 `GetDiskFreeSpaceExW`，时间用 `SetFileTime`。

### 3.6 断线和续传

**一次运行之内（重连）**：

- 每端的问候里有本次运行的随机编号。连接结束（`peer_left`）时传输进入 `RCS_FILE_WAITING`；同一端回来（观看端重连：分享端那里是新的观看端编号，问候里的运行编号相同）时，发送方把清单再发一遍（`OFFER` 带“重发”标志和“结果已知到第几项”），接收方：
  - 不认识这次传输（第一次的清单在断线时丢了）：当新的清单处理；
  - 还在等宿主决定：什么都不回，决定了再回；
  - 已经结束（例如宿主在对方不在时取消了）：回 `CANCEL`；
  - 进行中：把发送方不知道的条目结果再发一遍（`ITEM_DONE`，发送方忽略重复的），纪元加一，等存储把手里的写完，回 `ANSWER`：每项从接收方**已经收到**的偏移继续（这时也就是已经写好的）。
- 纪元的作用：接收方每回一次 `ANSWER` 纪元加一，发送方之后的块都带新纪元，接收方丢掉旧纪元的块和 `ANSWER` 发出之前的块，所以断线前在路上的块不会和新的混在一起。
- 在路上、对方没收到的最多是一个窗口（4 MiB），会重发；写好了的不再发。
- 等多久：`reconnect_wait_ms`（默认 60 秒，比观看端默认的重连窗口 30 秒长）。没等到就以 `FAILED`、`DISCONNECTED` 结束；对方回来时再告诉它（`CANCEL`）。
- 分享端的助手中途离开（`machine_left`，例如被新的助手替换）也一样：用到机器那一半的传输进入等待；接收方把“已收到”退回到“已写好”，纪元加一，新的助手接上（`machine_joined`）后回 `ANSWER`，发送方从已写好的地方继续；发送方把问了、还没读回来的块重新问新的助手。助手在 `reconnect_wait_ms` 内没回来就以 `DEVICE` 结束。

**跨运行（续传）**：

- **令牌**：每次传输有一个 16 字节的随机令牌（`rcs_file_transfer_info.token`，`RCS_FILE_OFFER` 里也有）。发送端宿主要支持续传就自己记下令牌和条目；下次运行用同样的条目、把令牌放进 `rcs_file_offer.resume_token` 再发。同一个令牌的传输还没结束时再发是 `INVALID_STATE`。接收端也一样：同一令牌收到的另一次传输还没结束时，`rcs_file_accept` 是 `INVALID_STATE`，两次会写同一批临时文件。
- **接收端宿主**看到 `RCS_FILE_OFFER` 的 `resuming` 为 1 和令牌，按自己记下的“令牌 → 目录”接受到同一个目录（不记也行：接受到别处就是从头传）。令牌是发送端的（随机，除非它的宿主给以前的一个），只是名字、不是凭据：模块不知道当初是哪个对端发的那次传输，续传会接着它写下的内容写，所以宿主只对当初那个对端（按宿主自己的身份控制）的续传清单接受到那个目录。
- **只有说了续传的清单才接着写（安全评估第二轮）**：准备的请求带着清单的“续传”标志；不是续传的清单，目录里有它的令牌的记录或临时文件就整次失败（`INVALID_STATE`，原因写明可用 `rcs_file_discard` 删），什么都不拿、什么都不删。不看这个标志的话，发送方（令牌是它选的）用别人留下的令牌发一个“新”清单，宿主看到的不是续传，机器那一半却接着别人写了一半的文件写下去，或者把它们当成以前的运行留下的删掉。
- **记录**：`keep_partial` 为 1（默认）、`SYSTEM` 时，接收端的机器那一半在目标目录里为每次传输写一个小记录文件 `.rcsdk-resume-<令牌的十六进制>`：开头是 `RCSDKFT1` 和令牌，之后每开始写一个文件追加一条“开始”（相对路径、发送端的大小和修改时间），每完成一个追加一条“完成”（以及实际存成的名字，改名的情况）。临时文件就是 `名字.<令牌的十六进制>.rcsdk-part`，和不续传时一样；续传的传输令牌不变，所以找得到上次写了一半的文件。
- **匹配**：接受一个清单时，机器那一半读这个令牌的记录（没有就是没有），每个文件按**相对路径、大小、修改时间**对：记录说完成了、存成的文件还在、大小对 → 这一项算完成（“以前的运行完成的”，不再发，也不再按 `on_conflict` 处理）；记录说开始了、临时文件在、是普通文件、不比文件大 → 从临时文件的大小继续（接着写之前再查一遍，见 3.5）；别的（发送端的文件变了、记录不在或没有这一项、临时文件没了、比文件大、是链接或管道）都从头写，那个名字上以前的运行留下的东西在接受时就删掉（是目录的不删，写的时候这一项失败）。发送端从 `ANSWER` 得知每项从哪里开始，`resumed_bytes` 两端一致。记录本身也当作不可信的输入检查（路径规则、长度），坏掉的尾部不要。
- **谁删**：
  - 传输完成：记录删掉（临时文件已经都改了名）。
  - 取消、拒绝，或者因为连接以外的原因失败：临时文件和记录删掉。
  - 因为连接或运行结束而失败（`DISCONNECTED`）：留下，`rcs_file_done_event.partial_kept` 和 `rcs_file_transfer_info.partial_kept` 为 1，等下次续传。
  - 宿主不打算续传了：`rcs_file_discard(session, directory, token)` 让机器那一半删掉这个令牌的记录和它列出的临时文件，完成后 `RCS_FILE_DISCARDED` 说删了几个；同一令牌的传输还在进行时是 `INVALID_STATE`。
  - `keep_partial` 为 0：不写记录；机器那一半停止时（运行结束、助手离开）删掉它写了一半的文件。代价是分享端的助手中途被替换时，正在写的那一项失败。
  - 程序崩溃时什么都来不及做：留下的就是临时文件和记录，下次续传或 `rcs_file_discard` 处理。
- **结束的顺序**：上面这些在 `RCS_FILE_DONE` 之前做完，宿主收到它时看目录，看到的就是最后的样子。传输结束时，会话那一半把结束要做的事作为这次传输的最后一个请求交给它的存储：收的一端完成时设目录的时间、删记录（`COMPLETE`），取消或失败时删临时文件和记录（`DISCARD`），留下续传文件时、发的一端、还没开始写时只关文件（`CLOSE`）。机器那一半一件一件按顺序做，做完回答 `ENDED`（它说明这次传输之前的请求也都做完了，没有文件还开着），会话那一半收到才送出 `RCS_FILE_DONE`；`rcs_file_get_transfer` 也是这时才显示 `FINISHED`，在这之前读到的是结束前的状态，取消、暂停已经是 `INVALID_STATE`。在 `OFFERED` 时结束的（清单还在等接收端的宿主决定）存储手里没有这次传输的事，立即送出。会话那一半交出请求就送出 `RCS_FILE_DONE` 的话，机器那一半在另一个线程（助手时在另一个进程）里还没做完，宿主可能还看得到记录、临时文件和没设时间的目录（Windows 上的测试发现过，Mac 上通常来得及）。
  - 机器那一半在回答之前离开（助手被替换或退出），或者结束时它不在：`RCS_FILE_DONE` 立即送出，没做完的留下，日志写明（没设时间的目录；`keep_partial` 为 1 时的临时文件和记录，`rcs_file_discard` 删，同一令牌的下次运行接着用）。运行结束时也一样（观看端的机器那一半先停）。
  - `target = HOST` 时一样：存储是调宿主回调的线程，`RCS_FILE_DONE` 等它做完之前排着的调用，之后不会再有这次传输的 `read`、`write`、`resume`。运行结束时不等，已经排着的调用还会来。
  - 发的一端的 `RCS_FILE_DONE` 可能比收的一端的早到（收的一端把最后一项的结果发出去后才做结束的事）：文件在不在，以收的一端的为准。
- **`target = HOST`**：模块不碰文件，续传由宿主自己的存储做：接受时对每个文件调 `resume` 回调（带令牌、路径、大小、时间），宿主返回已经有多少字节（0～大小；等于大小就算完成，大于大小这一项失败），`write` 从那里接着收；`partial_kept` 告诉宿主这次结束时该不该留着写了一半的数据。

### 3.7 事件和宿主的回调在哪个线程

- 会话那一半的事件照常在调用返回后交给宿主。宿主在 `on_event` 里调用模块的函数（`rcs_file_accept`、`rcs_file_cancel` 等）时，它们引起的事件由核心先存下，等那次 `on_event` 返回后在同一线程上送出（所有模块都一样，否则会死锁）。
- 模块自己有两个线程：节拍（超时、限速、进度、上面说的事件），和 HOST 时调宿主回调的线程；机器那一半有一个读写文件的线程。都在会话销毁或机器那一半停止时结束。

## 4. 两端和角色

两种角色都能发、都能收，各自的设置决定本端允许哪个方向；对方不允许时，`rcs_file_send` 立即返回 `INVALID_STATE` 并说明（对方在问候里说了它允许什么，变了有 `RCS_FILE_PEER`）。分享端有多个观看端时按观看端分别传。清单超过本端的 `max_items`、`max_offer_bytes` 时接收端的模块直接拒绝（`REJECTED`，`INVALID_ARGUMENT`，宿主看不到这个清单），本端不收文件时同样（`INVALID_STATE`）。

等本端宿主决定的清单（`OFFERED`）有预算：来自一个对端的最多 `max_pending_offers` 个（默认 100）、条目合计最多 `max_pending_items`（默认 20 000），所有对端合计最多 `max_pending_items_total` 个条目（默认 100 000）。新的清单在留下任何东西之前先算：超过哪一项就立即拒绝（`REJECTED`，`BUSY`，原因写明是哪一项，写日志），宿主看不到它，连接、画面和别的传输照常。接受、拒绝、超时或者别的原因结束的清单不再算。两个条目的上限都不能小于 `max_items`（否则什么都没在等时一个最大的清单也放不下，设置被拒）。没有总量的话，一个已经接入的对端可以不停地发合法的清单，每个都留着全部条目、都送给宿主，直到 120 秒后超时（代码审查时的测试：200 个各 500 项的清单全部到了宿主，AddressSanitizer 下多占约 138 MB）。默认值让正常使用碰不到：一个人连着发几十个清单、几个最大的清单同时等用户决定都放得下；宿主在 `on_event` 里直接决定的，清单根本不会排起来。

## 5. 安全

- 默认什么都不允许（`flow` 为 0），收到清单也要宿主明确接受：文件不会不经宿主就落盘。
- 路径规则保证写不出宿主给的目录；符号链接不跟随，所有写入通过打开的目录句柄，检查之后中间的目录被换成链接也写不到外面（见 3.5）。临时文件新建时独占，接着写之前查清楚是它自己的普通文件（见 3.5）。
- 对端不能靠发清单占满本端的内存：等决定的清单有预算（见第 4 节）。
- 无人值守时机器那一半在助手里：助手以 SYSTEM 运行（跟随安全桌面）时，文件也以 SYSTEM 的权限写，宿主给的目录要放在合适的地方。文档写清楚，SDK 不替宿主换身份。
- 收下的文件从不执行。
- 发送的一端：读源文件经条目的基准目录一段一段打开；列目录也经句柄（安全评估第二轮）：从宿主给的目录起，每一层用打开的目录句柄列出名字（POSIX 相对句柄打开 `.` 再 `fdopendir`，Windows 对句柄 `GetFileInformationByHandleEx(FileFullDirectoryInfo)`），每个名字相对句柄查（不跟随），是目录的再相对句柄打开（`O_NOFOLLOW` / `FILE_OPEN_REPARSE_POINT`）。看过之后被换成链接的目录以 `RCS_FILE_OTHER` 列出、不跟随，链接后面的名字、大小、时间都不进清单。按路径列（`opendir`、`FindFirstFileExW`、`lstat`）的话，能在共享树里写的进程在看过和列出之间把子目录换成链接，链接后面任何本账户能读的目录的文件名、大小就进了发给对端的清单（读内容已经经句柄，读不到）。宿主给的条目路径本身照旧解析（宿主的选择，和收的一端一样）。
- 一端的原因、日志里不写本机路径（安全评估 SA-16，见 3.5）。
- 对端不能靠反复重发清单或回答让一端为它读写的东西无限排队（安全评估 SA-11，见 3.4 的“流量”）。
- 续传只对说了续传的清单生效，令牌不是凭据（见 3.6）。

## 6. 统计

`rcs_file_get_transfer` 给每次传输的字节（完成的、续传的、经过连接的）和速度；模块的统计（`rcs_session_get_module_stats`）照常给收发的消息和字节。

## 7. 和画面抢带宽吗

不抢：模块消息和数据通道一样让路给画面（UDP 上画面在发时数据不发，数据的拥塞窗口按观看端的报告收放）。代价是画面占满带宽时文件传得慢；每次传输的上限 `max_bytes_per_second` 留给宿主，默认不限。
