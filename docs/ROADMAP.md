# 目标与路线

## 目标

- **定位**：通用的远程桌面与屏幕共享 SDK，给开发者用的库，不是面向最终用户的软件。独立的远程桌面和远程协助软件、嵌入在其他应用里的看屏和控屏、设备管理、云桌面，都用同一套接口。SDK 提供底层能力和丰富的接口：普通开发者只填核心配置就能用，默认值均衡；有特殊需求的宿主可以通过扩展深度定制每一项行为。
- **首版**：在局域网内，Windows 和 macOS 之间四个方向（Win→Win、Win→Mac、Mac→Win、Mac→Mac）都能做到 1920×1080、接近 60 FPS 的流畅观看，以及经过授权的键鼠控制；宿主可以通过 C/C++ 接口嵌入。
- **长期**：在已验证的设备和网络条件下稳定支持 3840×2160 / 120 FPS；支持公网直连和自建中继；按两端能力协商使用 H.264、HEVC 或 AV1。

## 首版验收标准

- 四个方向各连续运行 30 分钟：不崩溃、不死锁、不长时间黑屏，资源占用在预热后不持续增长。
- 记录每秒的帧率分布。以接近 60 FPS 为目标，不设单一的硬性门槛，但不能出现明显的卡顿和延迟累积。
- 键鼠控制有效；撤销控制、停止或断线后，不残留按下的按键。
- 反复启动 / 停止、连接失败、销毁时都能正确释放资源；权限被拒绝或撤销、网络断开、分辨率变化时，都能给出明确的状态。

## 下一步（建议顺序）

1. **收尾**：网络变化时保持连接的实机验证；iOS 的 iPad 实机验证；全面审查后新增的、需要有人在机器前的实机验证（macOS 锁屏和休眠时采集暂停与恢复、USB 耳机上的 Core Audio tap、拔显示器、HDR 亮度）；接口整理、常驻监听与重连、数据通道、TCP 中继的实机验证（Mac ↔ Windows 用 CLI 和 QML 示例跑通基本共享、运行中改设置、宿主送入画面、拔网线重连、剪贴板同步；经公网 coturn 的 TCP 中继，局域网的已验）；真实的 Win+L、UAC、改分辨率、开关 HDR；电源模块的真实网络唤醒和远程重启 / 关机 / 睡眠 / 注销（Windows PC 和 Mac），以及 Windows 无人值守：登录屏、锁屏和 UAC 下的采集与输入、Ctrl+Alt+Del（要用户先设置系统策略）、注销 / 切换用户、经 SCM 注册的服务开机后登录前连上（都需要有人在 Windows 前操作，见[指南 16](guide/16-unattended.md#windows)）；macOS 锁屏、休眠唤醒（可用 macOS 虚拟机）。
2. **小问题**：定位 Windows→Mac 4K120 偶发的一次恢复；分享的显示器的 HDR10 元数据（`rcs_hdr_metadata`）还没有哪个系统报告，恒为 0（Windows 可以从 `IDXGIOutput6::GetDesc1` 取）；Mac 发送端 4K 帧率受硬件编码器限制，可评估把“编码器能持续的帧率”报告给宿主，由宿主决定。
3. **无线和移动端的后续**：
   - **Wi-Fi 上声音被大块视频挤**：加过 `audio_dscp`（声音包标 EF），在家用 2.4 GHz 网状 Wi-Fi 上实测是取舍（缓冲放空少一半、补不回的丢包多 2～5%），默认不标。之后做了按路径速率发大画面（观看端量出瓶颈的速率，关键帧、整屏滚动超出路径 8 ms 的部分按它的 110% 发，留在分享端排队，声音在任何两个视频数据报之间插队；`path_pacing_percent`、`path_burst_us`，统计 `path_bps`、`sound_queue_us`、`sound_wait_us`）：本机模拟的 60 Mbit/s 空口上，声音时延的 p99 从约 175 ms 降到约 27 ms、播放缓冲从 200 ms 降到 54～60 ms，画面不变慢；欠载的次数没有变少（大画面隔得比播放缓冲记抖动的 8 秒还久时，缓冲在中间缩回去了，这是播放缓冲的事）（PERFORMANCE“Wi-Fi 上声音被视频挤”）。**还要在真实 Wi-Fi 上测**（S25+ 经 2.4 GHz 网状 Wi-Fi、5 GHz、另一台接入点，和 EF 对照），步骤在 PERFORMANCE 那一节。
   - **120 Hz 上既快又匀的呈现**（宿主的事，示例可以示范）：按显示链接给的刷新时刻每次刷新最多提交一帧；只按刷新周期定节奏试过，更差（PERFORMANCE“屏幕到屏幕，与 Moonlight 对比”）。每个系统的显示链接不同，要在 Mac 屏幕上反复测。
4. **待查**：局域网 30 分钟测试中，Windows 采集恢复时出现过一次 12～20% 的短暂丢包，码率被连降三次（见 PERFORMANCE）。**公网后续**：手机网络突发丢包时的恢复（可考虑 FEC 或长期参考帧，减少整帧关键帧）；更长时间的公网稳定性运行。
5. **尚未开始的功能**（需要逐项讨论后再做）：见下文“通用化还缺的能力”，以及 AMD 的 AMF 直接调用（要有设备才能调优，NVENC、2026-10-12 的 oneVPL 是先例）。麦克风和观看端回传声音已做。日志（按会话、助手区分）、P2P、中继、动态码率（规则可调、宿主可以自己决定）、声音、画质请求、运行中修改、单独传送的指针、宿主自己的画面 / 声音 / 输入、宿主自己的传输、宿主自己的编解码器已经完成。**D3D12 编解码后端决定不做**：RTX 4090 上实测，试过的 D3D12 帧（D3D11 解码后复制进共享纹理、加栅栏）和 D3D11 帧测不出差别，时间都花在硬件解码本身，原生 D3D12 解码也缩短不了；Moonlight 在 Windows 上也是用 D3D11 解码和渲染。D3D12 帧已删除，解码留在 D3D11 / Media Foundation 上（见 PERFORMANCE“D3D12 解码值不值得”）。
6. **安全评估**：已使用临时 ECDH（前向保密）和认证加密；2026-10-11 起做过几轮防御性的安全评估并修了发现的问题（[SECURITY-ASSESSMENT](SECURITY-ASSESSMENT.md)，修复状态和残余风险在那里）；还没有外部的审计。
7. **按网络调整帧率和分辨率**：已做（`rcs_video_tuning_config.degradation`：默认降帧率，可选按档缩小尺寸或两者兼顾；`size_percent`、`limited_ms` 可见），会话测试在本机限速代理上验证。还缺：手机网络、真实限速路径上的效果和档位阈值的实测。（另：Windows 发送端每帧纹理复用，P95 可省约 1 ms，低优先级。）
8. **首版验收**：四个方向的长时间运行测试（Mac→Mac 可用 macOS 虚拟机）。
9. **宿主集成**：把 QML 示例里的 `RemoteVideo` 整理成可以直接放进宿主工程的组件（仍在 `examples/`）；其他语言的绑定建在 C 接口之上、放在 SDK 之外。
10. **输入扩展**：复制粘贴文件已做，等真机验证（见上面的表）；拖放另设计（多显示器已做，联合桌面由观看端按各路的位置拼；文本、媒体键、触摸、笔、相对移动已完成；交给宿主的输入类型、文本插入点已实现；剪贴板已实现，是官方模块）。手柄暂不做，见下面。
11. **已确认的设计，按这个顺序做**（2026-10-08）：文件传输模块（已做）→ 异步准入（已做）→ 公网体验（FEC、参考帧失效；超时已做）→ 观看端回传声音（已做）和观看端的编码包（已做）→ 多显示器（已做）。预设已做，取值待实测。参数的自我描述、助手拆成自己的库：先不做。

### 暂不做

- **Linux 上的分享端和控制端**（2026-10-11 决定：不做，Ubuntu 的平台层放弃，设计稿已删；2026-10-12 补充：转发器是服务器，在 Linux 上运行，只有分享和观看、控制的两端不支持 Linux；2026-10-10 曾定只支持 Ubuntu 24.04 / 26.04，2026-10-09 曾定不做）。可移植的代码在 GCC / libstdc++ 上编得过，只为在 Linux 上跑测试。
- **浏览器的 WebRTC 和 P2P 直连**（2026-10-11 决定）：浏览器观看端只经宿主自己的通道连接（`RCS_TRANSPORT_HOST`：WebSocket，或宿主的 WebTransport 等），SDK 不内建 WebRTC 数据通道或 P2P 直连，也不为它预留接口；有明确的需求时再考虑。
- **手柄**（曾经加入，后来删除）：用处小，开发成本和跨平台成本都高。Windows 上系统的注入接口（Windows.UI.Input.Preview.Injection）只给开发者模式或打包的程序用，而且读到的程序只在前台时有读数；用 XInput 的游戏要内核驱动（ViGEm 一类：虚拟手柄能用，刚接上时的几个状态会丢，要重发）；macOS 上虚拟 HID 设备要向苹果申请权限，库带不了。以后要做时，作为新的输入类型和事件加回来（`host_input_types` 已经让宿主可以自己执行某几类输入）。

## 全面评审留下的（2026-10-07）

评审分四个方面：核心正确性、平台层、接口和文档、性能与局域网延迟。已经修掉、做掉的行已删去；下面是还没做的，按价值排列：

| 项目 | 说明 |
| --- | --- |
| 线程和 GPU 优先级 | SDK 的采集、编码、网络、输入线程都是普通优先级（只有声音用 MMCSS）；Sunshine 提高线程优先级并设 GPU 调度优先级。在 RTX 4090 满载时实测：采集设备 GPU 优先级 +7 加线程最高优先级，按键到画面没有可分辨的改善（见 PERFORMANCE），暂不做；CPU 满载（编译）时还没测 |
| 观看端的呈现路径 | 每帧带“已有更新的帧在排队”的字段（Moonlight 的做法是丢掉旧帧）。立即呈现的写法见指南 08（[怎样画得快](guide/08-viewing.md#怎样画得快)）；QML 示例晚约 15 ms 的问题已修 |
| 其他延迟项 | Media Foundation 编码器的纹理池（Windows 的硬件解码器 2026-10-13 起已用：Media Foundation、NVDEC、oneVPL 交出的纹理都放在池里，Intel 核显上每帧省 1～10 ms，PERFORMANCE）；采集着色器一遍直接写进 NVENC 的 NV12 输入；`input_boost_ms` 默认值（实测 P50 省约 4 ms，交互时多约 15% 的帧）。（DSCP、FEC、参考帧失效已做） |
| 隐私模式 | 无人值守和设备管理：分享时让本地屏幕变黑、挡住本地输入 |
| 待定位 | Windows 4K HEVC 观看端 30 分钟私有内存增长约 5 MiB（一次长时间运行）；`viewers_rate` 和三个观看端 1.5 s 内停止的时间门限在 ThreadSanitizer 下会超 |

| **Windows 在 AMD 的 GPU 上解 HEVC 4:4:4**：Windows 自带的 HEVC 解码器只在 CPU 上解 4:4:4（这台 PC 上滚动的彩色文字 1080p 每帧约 35～38 ms、要 3 个核）；在 GPU 上它收下画面却不交出，而 RTX 4090 和 Intel 核显都有 HEVC 范围扩展的 D3D11 解码档次。NVIDIA GPU 上已由 NVDEC 解（`RCS_BACKEND_NVDEC`，2026-10-12：1080p 每帧约 3～5 ms，4K 约 6～8 ms），Intel GPU 上已由 oneVPL 解（2026-10-13：1080p 约 6 ms，4K 约 15.5 ms，见上表“Windows 解码后端 oneVPL”）。双显卡机器上 `HARDWARE_FIRST` 按宿主设备所在的 GPU 选 | Windows 观看端要 4:4:4 又要 60 FPS、低 CPU（Mac 分享给 Windows 的远程办公、设计、代码） | AMD 和通用的：SDK 自己解析 HEVC 码流（SPS、PPS、片头、参考帧），填 DXVA 的图像参数交给 `ID3D11VideoDecoder`（Moonlight 经 FFmpeg 这样做），工作量大，先出设计 |

## 各系统的差别

同一套接口在每个系统上都一样，系统做不到的由 `rcs_capabilities` 报告、调用时以 `UNSUPPORTED` 和原因失败。对照表见开发者指南的[各平台的差别](guide/19-platforms.md)。

## 公网设计约束

- 宿主负责身份、配对或邀请、授权和信令通道；SDK 负责连接协商、候选地址选择、直连 / 中继切换、恢复，以及全部媒体与输入数据。
- 协商消息对宿主来说是不透明的字节：SDK 生成，宿主通过自己的任意通道转发，SDK 消费。后端用什么语言、什么协议都可以，SDK 不绑定任何业务服务器。
- 优先直连，失败时走宿主自己部署的中继。中继只转发端到端加密的数据，不具备控制权限。ICE / STUN / TURN 是候选标准。
- 视频优先保证时效（帧龄预算、关键帧恢复）；按键和按钮事件要可靠、有序、可释放；鼠标移动可以合并。控制数据不能被视频发送队列长时间阻塞。
- 可选的服务端组件（信令编解码、凭据校验、地址探测、中继）独立发布，不并入端侧 SDK。
- 局域网的测试结果不能外推到公网，公网要单独验收。

## 工作方式

每项改动都要先确定要解决的瓶颈，再验证效果。构建通过、本机通过、跨机通过、跨平台通过要分开报告；性能数据注明设备、显示器、分辨率、码率和测量终点。没有验证过的能力不写成"已完成"。
