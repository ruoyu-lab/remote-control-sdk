## 测量方法

- **响应时间**：被控端运行全屏 `rcsdk_latency_target`，观看端运行 `rcsdk_response_probe`。探针通过 SDK 发送空格键，目标窗口切换屏幕上的 32 条黑白标记，探针从解码帧中识别到新标记即结束计时。两次计时都在观看端同一个单调时钟上，不需要两台机器对时。终点是 SDK 交付解码帧，**不含**观看端绘制和显示器扫描。
- **帧率**：观看端统计 SDK 解码帧数（视频接收统计的 `decoded_frames`）。被控端必须有持续变化的画面，测试窗口每个显示刷新周期只重绘一小块区域。
- 探针为了识别标记，每帧要从 GPU 读回几行像素，在 Windows 上会让接收帧率下降约 3 到 4 FPS。测纯吞吐时应改用不注册帧回调的 `rcsdk_cli --role view`。

## Windows：NVENC 每种画面格式的帧率上限（2026-10-13）

一个宿主运行中把 4K 160 帧的 HEVC 4:4:4 换成 H.264 时，分享会话以 `NVENC: Initializing the encoder at 3840x2160 failed (invalid parameter, 8: Invalid Level.)` 结束。在 PC（RTX 4090，驱动 616.92）上用 `rcsdk_codec_timing --encoders --backend NVENC --size 3840x2160` 复现：

| 编码格式、画面格式 | 能编的 | 打不开的（Invalid Level） |
| --- | --- | --- |
| H.264 4:4:4 | 128 帧（每秒 4 147 200 个宏块，Level 6.0 以内） | 129 帧（4 179 600，要 6.1）、160 帧 |
| H.264 4:2:0 | 160 帧（要 6.1） | — |
| HEVC 4:4:4 | 240 帧（要 6.1） | — |
| AV1 4:2:0 | 240 帧 | — |

驱动对 H.264 报的最高 Level（`NV_ENC_CAPS_LEVEL_MAX`）是 6.2，4:4:4（High 4:4:4 Predictive）实际只到 6.0；显式设 Level 6.0、6.1、6.2 也一样打不开。所以 SDK 列实现时，4:4:4 从最高 Level 往下，各试一次刚好超出下一级的 4K 帧率，第一个打得开的就是它的 Level。这块卡上试 H.264 4:4:4 三次、HEVC 4:4:4 和 4:4:4 10 位各一次，共约 100 ms，每个进程一次。`rcsdk_cli --info` 列出每种画面格式 4K 最多多少帧：H.264 4:2:0 515、4:4:4 128，HEVC 各格式 515。

## Windows：混合显卡上的 Media Foundation 编码器（2026-10-13）

同一台 PC，接线同下一节（4K 159 Hz 主屏接核显，1080p 165 Hz 接 RTX 4090）。这一天 DXGI 的第一块 GPU（Windows 默认给程序的那块）是 RTX 4090，两块显示器的输出在 DXGI 里都挂在 RTX 4090 名下；前一天改接后有一段时间核显是第一块，“NVDEC 解 4:4:4、直接调 oneVPL”一节最后一条的两处 `codec_roundtrip` 失败就出在那时。这一天没有再出现核显在前，没有改这台机器的显示和图形设置；下面第一条用挂钩再现。

- **NVIDIA 的 Media Foundation 编码器起不来**：它在激活（`ActivateObject`）时自己建一个 D3D11 设备，不指定适配器，也就是在默认 GPU 上（挂钩它的 `D3D11CreateDevice` 导入看到的），不管 `MFTEnum2` 是按哪块 GPU（`MFT_ENUM_ADAPTER_LUID`）列出它的。把它建的设备换到核显上（默认 GPU 是核显时的样子），H.264、HEVC、AV1 三个都激活失败，`E_UNEXPECTED`（0x8000FFFF），每个约 70～100 ms（驱动 616.92）。混合显卡笔记本默认就是这样（显示器接核显，程序默认在核显上）。现在默认 GPU 不是 NVIDIA 的时候，实现列表先激活一次 NVIDIA 的 Media Foundation 编码器，起不来的不列出（日志说明）；指定 Media Foundation 时以 `UNSUPPORTED` 失败，原因写明 HRESULT 和这条限制。NVENC 不受影响（它用采集设备本身）。默认 GPU 是 NVIDIA 的时候不多花时间（激活一个要 0.1～0.4 s）。
- **Intel 的 Media Foundation 编码器不跟随改码率**：恒定码率（CBR）下，流中设 `CODECAPI_AVEncCommonMeanBitRate` 返回 `S_FALSE`，读回仍是原值，码流不变；SDK 以前把 `S_FALSE` 当成接受（`bitrate()` 报告了新值）。和接线无关：`codec_roundtrip` 以前只在排第一的 Media Foundation 编码器上测改码率，核显在前时才轮到 Intel 的。峰值受限的 VBR（峰值 = 目标）下它接受并跟随；NVIDIA 的正好相反。现在打开时先用 CBR，流中试改一次，不接受的换成峰值受限 VBR，峰值随目标走；`S_FALSE` 算拒绝。`codec_roundtrip` 改为在每块 GPU 的每个实现上测改码率。

改码率（640×360、30 FPS、带细颗粒的渐变，2 → 0.2 Mbit/s；改后 30 帧的字节数 / 改前 30 帧，驱动同上）：

| 编码器 | CBR | 峰值受限 VBR |
| --- | --- | --- |
| Intel H.264 | 280065 / 285429（98%） | 41777 / 278792（15%） |
| Intel HEVC | 279367 / 285869（98%） | 29934 / 250621（12%） |
| Intel VP9 | 188469 / 164831（114%） | 36830 / 155562（24%） |
| NVIDIA H.264 | 21148 / 263540（8%） | 263737 / 263540（100%） |
| NVIDIA HEVC | 17821 / 261890（7%） | 261941 / 261890（100%） |
| NVIDIA AV1 | 13888 / 236133（6%） | 242209 / 236133（103%） |

- Intel 的 VBR 在 0.2 Mbit/s 时实际约 0.33 Mbit/s（H.264；这种画面量化已到上限），不像 CBR 时完全不动。
- 表里 90 帧都带颗粒。`codec_roundtrip` 的检查前 30 帧是平滑的渐变（像以前的往返测试）：微软的软件 H.264 编码器从第一帧就是颗粒时，头两个关键帧之后量化一直在上限，改码率前后都是每帧约 3.5 KB，测不出跟随。按测试的画面，Intel 的 H.264、HEVC、VP9 改后是改前的 10%、8%、4%，微软的软件编码器 19%。
- **采集**：核显接的 4K 主屏挂在 RTX 4090 名下，Desktop Duplication 在 RTX 4090 的设备上拿到它的画面（Windows 跨适配器复制），按 30 FPS 采 1.5 秒得 47 帧，测试窗口的颜色正确，NVENC 和 NVIDIA 的 Media Foundation 编码器在这个设备上编。核显在前（或程序被设成节能）时它挂在核显名下，采集和编码都在核显上；这种排列没有测。

## Windows：Intel 核显上 oneVPL 解码，解码器的纹理池（2026-10-13）

同一台 PC：RTX 4090（驱动 616.92）和 Core Ultra 7 270K Plus 的 Intel 核显（驱动 32.0.101.8860，oneVPL 运行时 `libmfx64-gen.dll` 26.05.06）。显示器还是前一天改接后的样子：4K 159 Hz 的主屏接在核显上，1080p 165 Hz 的接在 RTX 4090 上；DXGI 的第一块（默认）GPU 是 RTX 4090。工具和方法同下一节（`rcsdk_codec_timing`，白底彩色文字、上半屏滚动，60 FPS 的节拍送 11 秒、去掉第 1 秒，600 帧；解码器的时间从交出包到画面在 GPU 上画完，CPU 是这段时间里进程每帧的用户加内核时间）。码流：HEVC、H.264、AV1 由 NVENC 编（排第一的硬件编码器），VP9 4:4:4 由 libvpx 编（没有硬件编码器编它）。比 4:2:0 时 Media Foundation 的硬件解码器用 `--gpu Intel` 放在核显上，和 oneVPL 在同一块 GPU 上。每项测一到三次，几次的写成范围。

## ARM64 上的密码学指令（2026-10-13）

BearSSL 在 ARM64 上只有常量时间的软件实现（位切片的 AES、C 写的 SHA-256），2 核虚拟机里的转发器约一半的 CPU 花在逐跳加密上（[“转发器的吞吐”](#转发器的吞吐2026-10-12)的 `perf`）。现在 BearSSL 后端在 ARM64 上用 SDK 自己写的 ARMv8 密码学扩展指令（`src/crypto/bearssl_armv8.cpp`）：AES-CTR 用 AESE / AESMC，8 个块一起过每一轮；SHA-256 用 SHA256H / H2 / SU0 / SU1，HMAC、PBKDF2 都走它。处理器没有这些指令时照旧用 BearSSL 的软件（Linux、Android 看 `getauxval(AT_HWCAP)`，Apple 的 ARM64 都有）。Android 上每张画面的加密、解密，Linux 的转发器的逐跳加密都走它；系统的密码学（macOS、iOS、Windows）不变。

**单线程的吞吐**（`rcsdk_test_crypto_armv8 --bench`，MB/s = 每秒 10^6 字节，BearSSL 的软件 → 指令）。“CTR + HMAC”是 `Aead::seal` 做的事：复制明文、AES-256-CTR、HMAC-SHA256（每次重算密钥的填充，和 `crypto::hmacSha256` 一样）。三处都在同一颗 M4 Pro 上：Mac 是 `-DRCSDK_CRYPTO_BACKEND=bearssl` 的 `release`（Apple clang 21），虚拟机是 Parallels 的 Ubuntu 24.04.3 ARM64（GCC 13.3），模拟器是 Android 16 的 arm64 AVD（NDK r27 的 clang 18，按 `getauxval` 选）：

| 字节 | AES-256-CTR：Mac / 虚拟机 / 模拟器 | HMAC-SHA256 | CTR + HMAC |
| ---: | --- | --- | --- |
| 64 | 161 → 5812 / 194 → 5519 / 174 → 6024 | 82 → 469 / 84 → 467 / 82 → 495 | 54 → 436 / 58 → 387 / 56 → 520 |
| 1200 | 174 → 11172 / 210 → 10714 / 192 → 11082 | 365 → 2095 / 352 → 2355 / 368 → 2446 | 115 → 1658 / 130 → 1785 / 124 → 1896 |
| 16384 | 178 → 12501 / 215 → 12072 / 196 → 12932 | 427 → 2465 / 409 → 2822 / 438 → 2826 | 123 → 2049 / 141 → 2275 / 135 → 2345 |

AES 快 28～70 倍，HMAC-SHA256 约 6 倍，一个 1200 字节的数据报封装约 14 倍（约 10 µs → 0.7 µs）；之后 HMAC 占了封装的大半。S25+ 真机没量（高通的核，结果会不同）。

- **每个观看端的代价**（100 人以上的斜率）：4 Mbit/s 约 0.57% 个核，8 Mbit/s 约 0.85%；出口每 Mbit/s 约 0.1～0.13% 个核，一个核约 800～1000 Mbit/s（之前 370～500）。负载轻时不按人数线性：25 人和 50 人 × 8 Mbit/s 都是 41～44%，50 人 × 4 Mbit/s 39%。原因没查清，推测是 Mac 把闲的虚拟核线程放到能效核上（同样的活儿记的 CPU 时间更长），真实服务器上要另量。75 人 × 8 Mbit/s 有一轮 102%（另两轮 63%、64%），也没查清。
- **剩下的时间花在哪**（`perf`，50 人 × 4 Mbit/s，39% CPU）：virtio 的通知（`vp_notify`）21%，SHA-256（指令）5.6%，AES-CTR（指令）1.9%，线程唤醒（`__wake_up_sync_key`）4.4%，软中断 4.3%，其余零散（`sendto`、复制、`malloc`）。之前同样的负载里 BearSSL 的 AES 和 SHA-256 占 42%（约 28% 个核），现在 7.4%（约 3% 个核）。150 人时 `vp_notify` 还是 23%：下一步是一个端口批量发（已做，两样合起来见[“合起来”](#合起来2026-10-13)）。
- **Mac 本机环回**上同一个转发器换成 BearSSL（`-DRCSDK_CRYPTO_BACKEND=bearssl`，现在用指令）和系统的密码学（CommonCrypto）一样：50 人 × 4 Mbit/s 61～62% 对 62～64%（两轮），25 人 × 8 Mbit/s 60 FPS 51% 对 52%，延迟相同；之前 BearSSL 的软件是 96% 和 88%。
- 没有这些指令的 ARM64（例如树莓派 4 的 Cortex-A72）照旧用 BearSSL 的软件，按“转发器的吞吐”一节的数字。x86-64 上 AES 本来就用 AES-NI，SHA-256 仍是 BearSSL 的软件（BearSSL 没有 x86 的 SHA 扩展），没量。TURN over TLS 的 AES-GCM 还是 BearSSL 自己的。

## Windows：NVDEC 解 4:4:4、直接调 oneVPL（2026-10-12）

那台 PC：RTX 4090（驱动 616.92，`nvcuvid.dll` 7.17.16.1692）和 Core Ultra 7 270K Plus 的 Intel 核显（驱动 32.0.101.8860，oneVPL 运行时 `libmfx64-gen.dll` 26.05.06）。这一天 4K 显示器改接在核显上（1080p 的接在 RTX 4090 上），表里的数字都是这样接的时候测的。工具 `rcsdk_codec_timing`（`tools/codec_timing.cpp`）：画面是白底上的彩色文字，上半屏每帧往上滚 3 像素、下半屏不动；画面先上传成编码器所在 GPU 上的 BGRA 纹理（和采集给的一样）；按 60 FPS 的节拍送 11 秒，去掉第 1 秒，600 帧。编码器的时间从交出画面到拿到包（含 GPU 上转成编码器要的布局）；解码器的时间从交出包到画面在 GPU 上画完（等它的栅栏），也就是 `on_gpu_frame` 拿到的样子（NVDEC 和软件解码器都是 BGRA8 纹理）；CPU 是这段时间里进程所有线程的用户加内核时间除以帧数。每项测一到两次，两次的写成范围。

**HEVC 4:4:4 的解码**：NVDEC（RTX 4090）和 Windows 自带的软件解码器（HEVCVideoExtension，CPU）解同一路码流。码流来自这台 PC 上排第一的硬件编码器：第一次 oneVPL（核显），第二次 NVENC（RTX 4090）。

## 转发器的吞吐（2026-10-12）

一台转发器（`server/forwarder`，[指南 24](guide/24-forwarder.md)）带得动多少房间和观看端、CPU 和内存多少、先在哪里撑不住。**只在本机环回和虚拟机里量过**：不是公网，也不是真实服务器的网卡，x86-64 服务器没有量。

**方法**：`tools/` 的 `rcsdk_forwarder_load`（[用法](../tools/README.md#转发器的负载)）。每个房间一个合成的分享端；每个观看端是 SDK 自己的那一跳（握手、逐跳加密、确认、报告、补要、校验、节流、动态码率都是 SDK 的代码），只是不跑管道里端到端的连接、不开封、不解码，画面里明文带着发出时间和序号（转发器从不看里面）。所以转发器这边和真的观看端一样，而一台 Mac 能放几百个。分享端：画面平均大小 = 码率 ÷ 8 ÷ 帧率（普通帧 ±25%），开始时和转发器要时各一个 6 倍大的关键帧；声音每秒 100 个 120 字节的包；每个观看端每 250 ms 经管道发一个数据报、分享端送回（控制和输入的往返）。**画面延迟** = 分享端把画面交给它那一跳 → 观看端那一跳交出整帧（两跳的节流加转发器，分享端和观看端在同一进程，同一个时钟）。每组预热 4～6 秒、量 12 秒，转发器每组重新启动。CPU 100% = 一个核；“出口”是观看端那一跳收发的字节（几乎全是转发器发给它们的；虚拟机里是网卡的发送计数）。

| 负载 | 同一台 Mac 上，和转发器抢 CPU（表里分开计：“负载 CPU”） | 在 Mac 上，经 Parallels 的共享网络（virtio-net）；虚拟机里 `rcsdk_forwarder_load monitor` 每秒读转发器进程和网卡。不把负载也放进虚拟机：2 个虚拟核会被它分走一半 |

  之前（只有批量发送）逐跳加密约占 60%，现在 13～19%；剩下的大多是每个包、每次唤醒在内核里的固定代价：每个 `sendmmsg` 让 virtio 通知一次宿主（虚拟机退出一次；物理机的网卡没有这一项，云主机的虚拟网卡多半也有类似的通知），每个观看端每秒约 180 次被唤醒。再省要动线程模型（下面“没做、量过的大改”的事件循环、同一张画面和声音给各个观看端的数据报放进一次 `sendmmsg`）。一个房间的分发在分享端那个端的线程上（`Forwarder::serve`，`perf` 按线程分）：250 人 × 8 Mbit/s 时它约 20～30% 个核，到一个房间 256 人的上限也不会先卡在它。

### TCP、WebSocket 入口一批一次写（2026-10-13）

一个端那一跳一轮封好的数据报（最多 64 个）经 UDP 一次 `sendmmsg`（[“批量发送之后”](#批量发送之后2026-10-13)），经 TCP、WebSocket 入口原来还是一个一个写：每个单独加帧（两字节长度或 WebSocket 帧头）、拿一次那条连接的锁、一次 `send`。现在 `RouteDemux` 把一批里发往同一条连接的数据报一起交给入口（`SendBatch`），入口在那条连接的锁下把它们一个接一个加好帧放进待发的缓冲，一次 `send` 写出。**线上的格式不变**：每个数据报仍是自己的一帧，WebSocket 上仍是一个数据报一条二进制消息（浏览器包就这样读），只是一次 TCP 写里有几十帧。端那边同一条路也一样改了：`FramedSocket`（端经 TCP、WebSocket 入口连转发器，观看端连分享端的 TCP 端口，TURN over TCP）和分享端的 TCP 端口（`TcpDemux`）也是一批一次写。Windows 上一个端那一跳本来每封好一个数据报就发（一批一个），不变。

**背压**仍按数据报算，和原来一样：一个数据报放进去会让待发的超过上限（入口每条连接 256 KiB，`TcpDemux` 256 KiB，`FramedSocket` 64 KiB）时，先把待发的按连接收得下的写出去（连接这次只收了一部分时，这一批里不再试）；还放不下就整个丢掉（`RouteDemux` 记作拒收：像满了的 UDP 套接字丢一样，交给那一跳的重传和码率控制），这一批后面放得下的（声音包、确认这类小的）照样放进去。所以一批的尾巴放不下时，大的丢、小的照走，丢的从不是半个帧。`forwarder` 测试的 `entryBatches` 在对端不读时往两种入口各塞约 32 MB（大小交替）：收到的按序、完整，收到 + 拒收 = 发出，大的丢了之后小的还进得去，之后连接照常；`websocket` 测试对 `FramedSocket` 的两种分帧做同样的事。

### 批量发送之后（2026-10-13）

- Mac 上负载轻时延迟里有 CPU 从空闲醒来的时间：慢观看端那组里代理的线程一直忙，同样 10 人 × 4 Mbit/s 的 p50 是 0.9 ms 而不是 2.5 ms。
- **延迟随一个房间的人数线性变长**（约每人 0.1 ms）：同一张画面在同一时刻发给每个人，最后一个人等前面所有人的那份发完。人分在多个房间时没有这个问题（下面 30 个房间各 3 人 p50 0.8～1.5 ms）。
- **先撑不住的地方**（批量发送之前；之后见上一节）：
  - Mac：**一个 UDP 端口的发送一个接一个**（所有端那一跳经同一个套接字发，`UdpSocket` 的互斥量；XNU 每次发送都持着套接字的锁），出口 650～870 Mbit/s、150～200 个端时开始大量重传、延迟上去，而转发器才用 2～3 个核（14 个里）；200 人 × 4 Mbit/s 崩到秒级延迟。采样（`sample`）里各端那一跳的线程约四成时间在等这把锁。改成让发送一起进内核在 Mac 上更糟（见下面的改动 1）；改成一批拿一次锁才好（改动 3）。
  - 虚拟机：**CPU**。2 个核用到约 90% 之前延迟平稳增长（150 人 × 4 Mbit/s、75 人 × 8 Mbit/s 还能看），用满就崩成秒级延迟、掉帧（200 人 × 4 Mbit/s、100 人 × 8 Mbit/s）。按 75% 留余量：2 个核约 120 人 × 4 Mbit/s 或 70 人 × 8 Mbit/s（p95 约 15～18 ms）；批量发送之后约 170 人或 100 人。
- **重传**：100 人以上两边都有重传，但两边系统的套接字缓冲都没丢（macOS 的 `dropped due to full socket buffers`、Linux 的 `RcvbufErrors` / `SndbufErrors` 都没变）：丢在本机环回的发送队列和虚拟网卡上。观看端都补回来了（丢失的画面 0）。

### 虚拟机里转发器的时间花在哪（`perf`，50 人 × 4 Mbit/s，65% CPU）

批量发送之前（之后的见上一节）：

| | 占转发器 CPU |
| --- | ---: |
| 逐跳加密：AES-256-CTR（BearSSL 位切片） | 34% |
| 逐跳加密：HMAC-SHA256（BearSSL） | 18% |
| `sendto` 到网卡（其中 virtio 的通知 16%） | 28% |
| 其余（节流、计时、线程唤醒、分片和复制） | 约 20% |

改动 1 之前同样的负载里还有 9% 是发送互斥量的 futex 唤醒。**一半的 CPU 是 ARM64 上 BearSSL 的软件密码学**：同一台 Mac 上把转发器换成 BearSSL（`-DRCSDK_CRYPTO_BACKEND=bearssl`）对比系统的密码学，50 人 × 4 Mbit/s 96% 对 64%（两轮），25 人 × 8 Mbit/s 60 FPS 88% 对 49%，延迟也多 1.5～2 ms。x86-64 上 BearSSL 用 AES-NI，AES 那部分会小得多（没量）；SHA-256 两边都是软件。2026-10-13 起 ARM64 上这两样用 ARMv8 的指令，同样的负载里只占约 7%，见[上面一节](#arm64-上的密码学指令2026-10-13)。

- 房间多时每人的 CPU 比一个房间多（10 × 5 比 1 × 50：Mac 多约 35%，虚拟机约 14%）：每个分享端的上传也要逐跳解密、重组，每个分享端也是两个线程。入口约是分享端数 × 码率 × 1.1。虚拟机前三行的分享端是固定码率（工具当时的默认），没有拥塞，不影响。
- 分享端那一跳的码率是动态的（SDK 默认，工具也照做）：转发器 CPU 满了、上行丢包时，分享端降码率（50 × 3 时从 4 降到 2.8 Mbit/s），观看端照常 30 FPS、延迟变长，不崩。工具的分享端改成固定码率（`--sharer-rate fixed`）时同样的负载崩了：转发器的接收缓冲满（`RcvbufErrors` 12 秒 219 万），重传把虚拟机的入口推到 2.1 Gbit/s（画面只有 220 Mbit/s），观看端 0.4 FPS。
- **过载时内存涨**：Mac 50 × 3 × 8 Mbit/s（出口要 1.2 Gbit/s，超过上面那个端口的上限）常驻 1.6 GB：每个观看端那一跳最多攒 8 MB 没发出去的画面（`maxQueuedVideo`）才丢。按最坏算内存：观看端数 × 8 MB。

### 慢的观看端、声音

- **一个慢的观看端**（经 2 Mbit/s 的瓶颈看 4 Mbit/s 的房间，10 人）：只有一档时它几乎看不到（转发器按设计每 2 秒让它从关键帧重来，量到 0.3 Mbit/s、丢包六成多），**其余 9 人不受影响**（Mac p50 0.9 ms、虚拟机 2.5 ms，0 丢失）；代价是关键帧：窗口里 5 个，分享端的码率多约 6%。分享端有四分之一码率的低档（`--encodings 2`）时，转发器把它当场移到低档，它 30 FPS、延迟约 20 ms，其余人照常。25 人 × 8 Mbit/s 60 FPS 里 3 个只有 1 Mbit/s 且丢 2% 的：低档（2 Mbit/s）它们也跟不上（约 3 FPS），只有一档时 0 FPS；其余 22 人两种都是 p50 约 2.4 ms、0 丢失。
- **声音按包算钱**（Mac，50 人 × 4 Mbit/s）：不带声音 50% CPU，每秒 100 包 66%，每秒 200 包（Mac 的 Core Audio 进程捕获 5 ms 一包）82%。一个声音包和一个画面分片的代价差不多（加密、`sendto` 各一次），而 4 Mbit/s 的画面每秒才约 420 个分片。

### 改动（每个都和改之前交替量过）

1. **Linux 上普通的 UDP 发送共用套接字的锁**（`src/transport/socket.*`：`std::shared_mutex`，只有要打 DSCP 标记的发送独占）。虚拟机：50 人 × 4 Mbit/s CPU 75.5% → 65.8%，延迟 p50 10.3 → 4.9 ms、p95 14.8 → 9.4 ms，重传 45 → 0；25 人 × 8 Mbit/s 60 FPS 66.2% → 57.8%，5.1 → 3.0 ms；25 人 × 4 Mbit/s 43.6% → 41.4%，5.7 → 3.8 ms。macOS **不改**：同样的改法在 Mac 上 50 人 × 8 Mbit/s 用了 11.7 个核，延迟 4.9 秒（XNU 每次发送持着套接字的锁，几十个线程抢它比在我们的互斥量上排队贵得多）。Windows 没量，不改。
2. **TCP、WebSocket 入口每个连接一把锁**（`server/forwarder/src/entry.*`：入口的互斥量只管连接表，每个连接的状态和写有自己的锁；原来所有观看端都在入口那一把锁下写，入口的线程读所有连接时也持着它）。虚拟机：TCP 25 人 × 8 Mbit/s 81.2% → 67.2%、p50 6.4 → 3.4 ms；WebSocket 50 人 × 4 Mbit/s 91.7% → 82.7%、12.9 → 6.3 ms、重传 632 → 85。Mac：TCP 100 人 × 8 Mbit/s p50 9.1 → 3.2 ms、p95 13.4 → 6.5 ms，CPU 206% → 230%（同时写得多，XNU 上更贵；50 人 × 8 Mbit/s 95% → 144%，延迟 4.8 → 2.4 ms）。
3. **批量发送**（2026-10-13；`src/transport/socket.*` 的 `DatagramSocket::sendBatch`、`DatagramBatcher`，`src/protocol/udp_connection.cpp` 一轮的发送攒到 `flush()`）：一个端那一跳一轮封好的数据报（最多 64 个）一起交给套接字；Linux（Android 也是）上 `sendmmsg` 加 UDP GSO，DSCP 标记作为每个消息的控制数据（`IP_TOS` / `IPV6_TCLASS`），套接字从此不用锁；macOS 上一批在锁下一个个发；Windows 不改。节流不变：一批只是这一轮放行的。数字见上面“批量发送之后”：虚拟机里 CPU 少 17～28%，150 人 × 4 Mbit/s 的 p50 16.6 → 9.1 ms，200 人 × 4 Mbit/s、100 人 × 8 Mbit/s 从崩变成能看；Mac 上 UDP 入口的 CPU 少 10～37%，一个端口到 1.3 Gbit/s 还不丢。
4. **TCP、WebSocket 入口一批一次写**（2026-10-13；`src/protocol/route_demux.*` 的 `SendBatch`、`server/forwarder/src/entry.*`，端那边 `src/transport/framed_socket.*`、`src/protocol/tcp_demux.cpp`）：一个端那一跳一轮的数据报经 TCP、WebSocket 一次写出，每个仍是自己的一帧（WebSocket 一条消息），线上格式不变；背压仍按数据报。数字见上面“TCP、WebSocket 入口一批一次写”：虚拟机里 150 人 CPU 110% → 79%、p95 12 → 7 ms，Mac 上少 45～55%。

**没做、量过的大改**（数字见上）：
- **事件循环代替每端两个线程**：线程的等待和唤醒约 11%（批量发送之后；密码学指令也用上之后约 20%，每个观看端每秒约 180 次被唤醒，见“合起来”），加上节流的计时、分片和复制；几百人时 400 多个线程（虚拟机里 250 人 × 4 Mbit/s 时 CPU 187%、没满就崩了，原因没查）。换成少数几个线程轮流服务要重写连接的线程模型；那样还能把同一张画面发给各个观看端的数据报放进一次 `sendmmsg`（现在一次只是一个观看端的）。
- **TCP、WebSocket 入口的线程只读可读的连接**：它现在每一轮对每条连接都 `recv`（150 人时每秒约 13 万次，多数什么也没读到），约 0.05 个核；要 `waitAny` 报出哪些可读。（一批一次写已经做了，改动 4。）
- 收的那边 `recvmmsg`：只占 3%，不做。

**还没量的**：公网（真实的丢包、延迟、NAT），真实服务器的网卡（虚拟网卡和本机环回的每包代价都和它不同；能自己切 UDP GSO 的网卡），x86-64 服务器（AES-NI），4 核以上的 Linux（一个接收线程、按核线性能不能延续），几小时的长跑，真的 SDK 观看端（解码）在这种负载下的体验，上千个端；Windows 上的批量发送（没做）；Android 上的 `sendmmsg` 和 GSO 只编译过，手机的 Wi-Fi 网卡上没试。

## Wi-Fi 上声音被视频挤：按路径速率发视频（模拟，2026-10-11）

只在 Mac（M4 Pro）本机回环上用模拟的 Wi-Fi 测过，**还没有在真实的 Wi-Fi 上测**。接口见[指南 13“动态码率”](guide/13-tuning.md#动态码率)。

**方法**：会话测试 `session.wifi_sound`（`tests/session.cpp`）。分享端是测试图案（1920×1080、60 FPS，每帧新的颗粒，VideoToolbox 硬件 H.264，目标 20 Mbit/s，动态码率从 20 Mbit/s 起）和测试音（每 10 ms 一个 Opus 包，带冗余）；观看端播放进一个不出声的设备（每 5.3 ms 取 256 帧，同 macOS 的默认周期），所以欠载和缓冲目标是 SDK 自己的播放缓冲给的。中间是 `ShapingProxy` 的空口模型：60 Mbit/s，排着的数据报按聚合帧发出（每个最多 4 ms 的空口，整个一起到），每个之前随机退避 0～0.4 ms，七分之一之前别的设备先占 0～4 ms，另加 2 ms 时延、200 ms 的队列。先跑 6 秒，让观看端重新开始收声音（播放缓冲没见过连接开始时的突发），4 秒后测 20 秒；其间观看端在第 1、10、19 秒各要一次关键帧（这种图案的关键帧约 730 KB，占这条链路约 100 ms 的空口；普通帧约 42 KB，约 6 ms）。声音的时延是分享端把包交给连接（编码包的 `on_audio`）到观看端拿到它（观看端编码包的 `on_audio`），画面的是采集到观看端拿到编码包；都是 p50 / p95 / p99 / 最大，ms。机器负载 3～5（改之前那两轮是另一时段，测 30 秒、4 个关键帧）。

- 不限速时，每个关键帧一次进了接入点的队列，跟在后面的声音晚到 170～220 ms，播放缓冲放空、之后按 200 ms（`max_delay_ms` 的上限）留着。按路径速率发时，关键帧超出 8 ms 的部分留在分享端，声音插到前面，最晚 40～46 ms，p99 从约 175 ms 降到约 27 ms，缓冲只留 54～60 ms。p50 不变（普通帧照旧一次发出）。
- 画面没有变慢：p50 一样，p99 从约 205 ms 降到约 92 ms（关键帧后面的几帧不再在接入点排在它后面；分享端的积压超过 40 ms 时少采一两帧）。关键帧自己仍要约 100 ms 的空口，最大值差不多。
- **欠载的次数没有变少**：关键帧隔 9 秒，比播放缓冲记抖动的 8 秒长，限速时缓冲在两个关键帧之间缩回 30 ms 上下，下一个 40 ms 的尖峰仍让它短短放空一次（补出的声音少一些：10～20 ms 对 18～32 ms）；不限速时第一次放空后缓冲一直留 200 ms。要让少见的大画面也不放空，得让播放缓冲记得更久，那是播放缓冲的事，这次没改。丢包两种都是 0。
- 分享端的 `path_bps` 是 58.6～59.2 Mbit/s（链路 60 Mbit/s）；`sound_queue_us` 读到的最大值和端到端的最大值一致（不限速 195～219 ms，限速 38～43 ms）；`sound_wait_us` 最多 0.4 ms。
- 开发中试过、不好的做法（数字是修掉一个让声音插队时丢掉视频分片的错误之前测的，只看相对）：所有画面（连普通帧）都按路径速率的 1.25 倍发，接入点的聚合帧变小、退避和别的设备占用的空口变多，估计一路往下走，画面的 p95 从 33 ms 到 59～93 ms；整帧（不只第一簇之后）比较到达和发出，聚合帧和分享端线程的停顿会把估计抬到瓶颈的两倍，关键帧又一次进了接入点；125% 时声音的最大值比 110% 大（97 对 42～67 ms）。
- 传输层的测试（`udp`）：20 Mbit/s 的有线瓶颈量出 19.6 Mbit/s，一帧 600 KB 之后 5 ms 发的声音按路径速率发时 11～14 ms 后到（`sound_queue_us` 同样），不限速时 223～242 ms；20 Mbit/s 节流着发一帧 300 KB 时，每 2 ms 一个的声音 20 个全部按序先到（48 ms），画面一个分片也不用补要。

## 丢包修复（2026-10-09）

冗余（FEC，`fec_mode`）的代价和效果，目前只有本机的数字：

- **编解码的花费**（M4 Pro，Release，单线程，`rcsdk_test_fec` 里量一次，机器上同时有别的构建）：一组 64 个 1200 字节的分片加 13 个冗余片（20%），算冗余 276 µs，丢 13 片时补回 282 µs。按这个速度，1080p 的普通帧（约 40 KB，一组）每帧约 0.15 ms；1 MB 的关键帧约 4 ms。每个观看端的连接各算一次。
- **传输层，回环**（`rcsdk_test_udp`：分享端的数据报约 5% 随机丢失，120 帧，普通帧 9 KB、每 30 帧一个 120 KB 的关键帧，每 4 ms 一帧）：固定 20% 时发了 316 个冗余片，补回 61 个分片，再要一次的 0 个，没有放弃的帧；不加冗余时同样的丢包全靠再要一次补回；`AUTO` 在报告显示丢包后加上冗余（补回 35 个，再要 1 个），丢包停了 5 秒后撤掉。
- **会话，回环**（`session.parity`：640×360 30 FPS，代理丢 5%）：固定 20% 时冗余补回的多于再要一次的，没有放弃的帧；运行中改成 `OFF`、`AUTO` 生效。
- **还没量**：真实的丢包路径上（Mac ↔ PC 经限速、加时延和丢包的代理，手机热点、公网中继）冻结的次数和时长、关键帧次数、实际帧率，开和不开冗余的对比；冗余在 4K 120 FPS 下占用的 CPU。

## 预设（待测）

四个预设（取值见 [API-DESIGN](API-DESIGN.md#6-预设的取值)）是按已有的测量和经验定的建议值，**还没有逐个在实机上量过**。要量的：

- 局域网（Mac M4 Pro ↔ Windows RTX 4090，有线），两个方向，每个预设：按键到画面（`rcsdk_response_probe --preset ...`）、帧率、实际码率、恢复次数。
- 整形代理上 4 Mbit/s、2 Mbit/s 的瓶颈加 50 / 100 ms 往返、1% 丢包：`BALANCED` 和 `LOW_BANDWIDTH` 的冻结次数和时长、稳定后的码率和帧率。
- `QUALITY` 的 4:4:4 在哪些编码器上真的用上（NVENC 能；VideoToolbox 和 Media Foundation 的 H.264 4:4:4 要逐个确认），文字的清晰度对比。

2026-10-09 夜里第一次跨机器（PC 分享、Mac 观看，H.264）：四个预设都跑通，`balanced`、`low-latency`、`quality` 约 60 FPS，`low-bandwidth` 30 FPS；按键到画面没量成（PC 屏幕上的防火墙对话框盖住了延迟目标，要有人在 PC 前处理）。

预设开发时在 Mac 本机回环上只做过冒烟（CLI 两端，`BALANCED` 和 `LOW_LATENCY` 都在 1080p 下约 62 FPS 解码；`LOW_LATENCY` 的一次运行开头丢了 6 个包，解码队列 4 帧 / 40 ms，另一次没有），不能当作测量结果。

## 编码器的速度与画质（2026-10-07）

`rcs_encoder_config.speed`：每帧花多少时间换画质。一个不在仓库里的测试程序：SDK 的编码器，按 60 FPS 节拍提交 GPU 上的 BGRA 纹理，两张不同的棋盘格交替（每帧都整幅变化，最难的画面），从提交到拿到包，去掉前 40 帧，每帧中位数 / P95（ms）。Windows 那台 PC：Intel Core Ultra 7 270K Plus 的核显（Media Foundation 里的 Intel 编码器，即 QSV）和 RTX 4090（NVENC）。

| 编码器、格式、尺寸 | FASTEST | BALANCED | BEST_QUALITY |
| --- | --- | --- | --- |
| Intel HEVC 1080p60 | 7.3 / 8.3 | 9.0 / 9.9 | 13.0 / 13.8 |
| Intel HEVC 4K60 | 9.7 / 11.2 | 11.7 / 12.8 | 17.9 / 18.8（只有 53 FPS） |
| Intel H.264 1080p60 | 7.8 / 9.1 | 7.5 / 9.3 | 8.3 / 10.5 |
| NVENC HEVC 1080p60 | 2.0 / 3.1 | 3.3 / 5.1 | 3.9 / 5.7 |
| NVENC HEVC 4K60 | 2.9 / 5.1 | 5.8 / 7.0 | 11.5 / 12.1 |
| NVENC H.264 1080p60 | 2.1 / 4.0 | 2.8 / 4.4 | 4.7 / 7.2 |

- 以前 Media Foundation 不设这一项，Intel 编码器用自己的默认值，和 BALANCED（50）一样；现在默认 FASTEST（0），Intel 的 HEVC 每帧少约 2 ms（1080p 9.0 → 7.3，4K 11.7 → 9.7），H.264 在噪声范围内（同一设置两次之间约差 1 ms）。NVENC 本来就是 P1（FASTEST），默认不变。
- 画质没有量：同样码率下 BEST_QUALITY 更好、FASTEST 更差，差多少取决于画面；桌面这种码率充裕的画面看不出来。
- **Intel 核显在 60 FPS 时会降频**：同一个 1080p 编码，按 120 FPS 提交每帧 5.9 ms（H.264）/ 5.6 ms（HEVC），按 60 FPS 提交 9.0 / 9.1 ms（BALANCED）。帧之间空闲时 GPU 降频，下一帧要等它升上来。SDK 不去占着 GPU 让它别降频（白耗电），宿主要更低的延迟可以开更高的帧率。
- **macOS**：VideoToolbox 的 `PrioritizeEncodingSpeedOverQuality`（FASTEST 设为真）对 SDK 默认用的实时编码器没有作用（M4 Pro，1080p H.264 4.95 对 4.94 ms，4K 16.3 对 16.4 ms，一个不在仓库里的测试程序）；只对可流水线的编码器有用（HEVC 1080p 6.5 → 4.7 ms，4K 没有变化）。Mac 的编码时间在硬件上，SDK 这边没有可省的。

## Windows 一台机器上的按键到画面（2026-10-07）

那台 PC 自己分享、自己观看：`rcsdk_latency_target`、分享端（`rcsdk_cli`，采集 4K 159 Hz 的主屏、NVENC）和 `rcsdk_response_probe`（观看端，解码在 RTX 4090 上）都在交互会话里，走 127.0.0.1 的 UDP，每次 40 个样本，终点是 SDK 交出解码好的帧（没有显示）。

| 格式 | p50 | p95 | p99 | 每帧解码 |
| --- | --- | --- | --- | --- |
| H.264 1080p60，20 Mbit/s | 29.0 ms | 40.7 ms | 42.4 ms | 0.45 ms（Microsoft H264 Video Decoder MFT，硬件） |
| HEVC 1080p120，30 Mbit/s | 24.0 ms | 31.7 ms | 33.0 ms | 0.43 ms（HEVCVideoExtension，硬件） |

- 解码只占半毫秒不到：NVIDIA 上换成直接调 NVDEC 省不下什么（硬件是同一块），所以不做。
- 没有网络的这 29 ms 里，SDK 管的是采集等下一次合成（159 Hz 约 6 ms 以内）、编码约 2 ms、发送和解码各不到 1 ms；其余是系统把按键交给程序、程序画出来、桌面合成，这些 SDK 改不了。帧率越高等的越少：120 FPS 比 60 FPS 的 p50 少 5 ms。
- **GPU 满载时**（一个不在仓库里的测试程序像游戏一样让 4090 一直忙：每次绘制 9 ms，两次排队），同样的 H.264 1080p60：帧率仍是 60，p50 从 28.8 / 30.5 ms 升到 35.7 / 36.7 / 50.4 / 48.3 ms（四次之间差得很大）。试过把 SDK 采集设备的 GPU 优先级设成 +7（非管理员也接受）、把采集编码线程提到最高：38.8 / 38.9 ms，和不提高的分不开。多出来的主要是满载的 GPU 拖慢了被操作的程序和桌面合成，SDK 自己的 GPU 工作提前也没用，所以没有做成选项（ROADMAP 里这一项改为“实测没有收益”）。

## UDP 发送节奏改动前后的按键到画面（2026-10-07）

这次改动改了 UDP 的发送节奏（每帧约 1 ms 内发完，以前按码率的 1.5 倍摊开）、不再定时插关键帧、Windows 上的等待用精确计时。同一条件下改之前和改之后的两个构建交替测三轮：Windows（RTX 4090，NVENC H.264）分享 4K 主屏，编码 1920×1080、60 FPS、20 Mbit/s，Mac 上 `rcsdk_response_probe` 每轮 30 个样本，有线局域网，UDP，终点是 SDK 交付解码帧。被控端的 `rcsdk_latency_target` 有两种画面：平常（只重绘一小块标记，像普通桌面操作）和 `noise`（整屏每帧都变，最坏情况；这时目标程序本身只能画到约 26 FPS）。

| 画面 | 构建 | 按键到画面 p50（三轮） | p95（三轮） | 帧率 | 丢帧 / 恢复 |
| --- | --- | --- | --- | --- | --- |
| 平常 | 改之前 | 35.4、35.1、37.4 ms | 43.8、42.5、46.7 ms | 60.2 | 0 / 0 |
| 平常 | 改之后 | 35.1、34.8、35.1 ms | 42.9、41.6、44.2 ms | 60.2 | 0 / 0 |
| 整屏变化 | 改之前 | 75.5、81.0、79.1 ms | 223.8、221.8、224.6 ms | 26.3 | 0 / 0 |
| 整屏变化 | 改之后 | 41.7、42.5、39.0 ms | 99.9、98.9、92.7 ms | 26.0～26.1 | 0 / 0（第一轮一次超时） |

平常的桌面操作每帧很小，发送节奏几乎不起作用，改之后平均快约 1 ms，在轮与轮的波动之内。整屏变化时每帧都很大，以前一帧要摊开发很久、后面的帧排在它后面，改之后 p50 从约 79 ms 降到约 41 ms，p95 从约 223 ms 降到约 97 ms。

## D3D12 解码值不值得（2026-10-07）

RTX 4090，回环，60 FPS，D3D11 帧（`d3d11_device`）对试验过的 D3D12 帧（`d3d12_device`，D3D11 解码后复制进共享纹理、加共享栅栏），各项是 p50 / p95（ms）：

| 画面 | 收到→回调，D3D11 帧 | 回调→显卡真正解完，D3D11 帧 | 收到→回调，D3D12 帧 | 回调→显卡真正解完，D3D12 帧 |
| --- | --- | --- | --- | --- |
| H.264 1080p | 0.95 / 1.84 | 2.43 / 4.57 | 0.88 / 1.55 | 2.35 / 4.55 |
| HEVC 1080p | 0.97 / 1.92 | 1.63 / 3.93 | 0.59 / 1.64 | 1.52 / 3.79 |
| H.264 4K | 0.50 / 1.36 | 4.61 / 6.99 | 0.46 / 1.10 | 4.37 / 7.01 |
| HEVC 4K | 0.62 / 1.28 | 3.52 / 11.78 | 0.95 / 1.45 | 3.25 / 10.04 |

D3D12 交接多出的一次复制和栅栏测不出来；时间花在硬件解码本身，原生 D3D12 解码也缩短不了它（Moonlight 在 Windows 上也是用 D3D11 解码和渲染）。所以删除了 D3D12 帧，也不做 D3D12 解码。

## Windows 编码后端：NVENC 与 Media Foundation（2026-10-07）

同一块 RTX 4090（驱动 616.92）上，直接调 NVENC（`RCS_BACKEND_NVENC`）和经 Media Foundation 的 NVIDIA 编码器（`RCS_BACKEND_MEDIA_FOUNDATION`）对比。

**每帧编码时间**：一个不在仓库里的测试程序，SDK 的编码器，喂 GPU 上的 BGRA 纹理，按帧率节拍提交，从提交到拿到包，去掉前 40 帧；画面像桌面：静止的渐变加一个占屏幕三分之一、文字一样的行在滚动的窗口。各跑两次，表里是两次的范围（ms）。

| --- | --- | --- |

| H.264 4K60，40 Mbit/s | 9.2 / 12.0～12.2 / 13.0 | 8.7～8.8 / 10.2～10.5 / **22.1～22.8** |
| H.264 4K120，60 Mbit/s | 7.3 / 8.0 / 8.2～8.3 | 4.6～4.7 / 5.4～5.5 / 8.3 |
| HEVC 1080p60，20 Mbit/s | 4.3～4.7 / 7.3～7.4 / 9.2～9.6 | 2.4～2.5 / 3.7～3.8 / 4.6～4.8 |
| HEVC 4K60，40 Mbit/s | 6.7～7.1 / 14.5 / 16.1 | 4.0～4.5 / 11.3～11.8 / 12.3～13.3 |
| HEVC 4K120，60 Mbit/s | 6.1～6.2 / 7.5～7.8 / 9.0～9.1 | 3.7～4.0 / 5.7～6.0 / 9.6～10.8 |

- NVENC 的 p50 每一项都更低，1080p 低 1.4～2.3 ms；p95 除 AV1 4K120 外也更低。H.264 4K60 的 p99 是例外：约 1% 的帧要 22 ms 以上（Media Foundation 13 ms），两种画面都这样，原因没查。

| --- | --- | --- |
| H.264 1080p60，20 Mbit/s | 38.8（49.9）、38.2（48.4）、39.6（45.3）、39.4（46.1） | 36.4（46.1）、36.2（48.2）、34.8（46.4）、39.9（49.5） |

平均快约 2 ms（H.264 1080p60：39.0 对 36.8；HEVC 4K120：38.5 对 35.4），和编码时间的差相当；每组样本少，单次之间相差几毫秒，有一次 H.264 两者持平。所以 `RCS_BACKEND_AUTO` 在 NVIDIA GPU 上先用 NVENC。AMD、Intel 没有测，仍用 Media Foundation。

## 动态码率的规则和宿主的决定（2026-10-06）

Windows 分享（`rcsdk_cli --host-pattern`：宿主自己的画面，1280×720 30 FPS，左上四分之一是编码器无法预测的噪点，上限 8 Mbit/s；NVIDIA H.264 编码器；会话 0 里的 SYSTEM 任务，不需要屏幕），Mac 观看，中间是 Mac 上的整形代理（3 Mbit/s 瓶颈、单向加 10 ms、队列 200 ms），有线局域网。每份报告由 `--rate-trace` 记下（约每 50 ms 一份），表里是第 10～18 秒的平均，即收敛之后。排队是 SDK 测得的路径排队，往返是 SDK 的往返时间。

| 规则 | 目标码率 | 到达 | 排队（最大） | 往返 | 宿主改过的决定 |
| --- | --- | --- | --- | --- | --- |
| 默认（30 / 60 / 10 ms） | 2254 kbit/s | 2372 kbit/s | 15.6 ms（53） | 27.7 ms | 0 / 372 |

## 宿主自己的传输经示例中继（2026-10-06）

`RCS_TRANSPORT_HOST` 走示例中继 `rcsdk_host_relay`（宿主服务器的替身，按房间原样转发），中继和分享端在同一台 Windows 上。Windows 分享（`rcsdk_cli`，交互会话），Mac 上 `rcsdk_response_probe` 每次 30 个样本，有线局域网，被采集的是 4K 主屏，终点是 SDK 交付解码帧。和直连 UDP 交替测量（直连时程序放在防火墙放行的路径上）。

## 声音延迟：Mac 采集后端与可调项（2026-10-04）

MacBook Pro（M4 Pro）本机，用 `rcsdk_audio_latency`（macOS）测量：从咔哒声进入系统混音，到经 SDK 采集、编码、UDP 回环、解码、缓冲、播放后再次进入混音。扬声器为内置扬声器。

| 采集 | 延迟 | 播放端断档 |
| --- | --- | --- |
| ScreenCaptureKit（每 20 ms 一块） | 88～106 ms，中位数 104.5 ms；12 次咔哒只测到 10 次 | 37 次 |
| **Core Audio 进程捕获（默认，每 240 帧）** | **67.4～68.4 ms** | 1 次（启动时） |
| Core Audio 进程捕获 + PCM | 64.4 ms | 1 次 |

- Mac 端采集到的声音因此快了约 37 ms，播放端也稳得多。这一项对 Mac → Windows 方向帮助最大。
- 采集周期 128 / 240 / 480 帧时，延迟都在 67 ms 左右，几乎不变：Core Audio 捕获本身有一段固定延迟，设备报告的输入安全偏移约 21 ms。
- 缓冲余量加 30 ms 后，延迟变为 96.1 ms，正好多出 29 ms。这同时验证了测量本身。
- 剩下的大部分来自系统：Core Audio 捕获的固定延迟、MacBook 内置扬声器的音效处理（设备报告 690 帧，约 14 ms）等。换成耳机或外接声卡会小一些。
- 本机测量时，录音器自己把设备周期设成了 128 帧，Mac 上同一设备的所有程序共用这个周期，所以 `playback_period_frames` 在这组测量里看不出效果。

**和 Sunshine / Moonlight 的对比**（读源码，2026-10-05）：

- 它们的 Windows 采集也是 WASAPI 共享模式环回，标志和本 SDK 相同，也是 Opus 受限低延迟模式，默认 5 ms 一包。声音走单独的 UDP（RTP）流，带前向纠错。
- Moonlight 的 SDL 播放端：内部队列超过 30 ms 时丢弃，SDL 队列最多约 50 ms；连接后先丢掉前 500 ms 的声音来对齐。它的观看端缓冲并不比本 SDK 的 14～20 ms 小。
- Sunshine 在静音时也持续发送（“continuous audio”），本 SDK 同样这样做。
- 本 SDK 还没有的：声音的前向纠错，用于弱网，不影响延迟。

**Windows 独占输出**：开发中试过，后来去掉了。它在 Minifuse 2 上能做到 3 ms 周期，但只改善 Windows 播放这一端，独占声卡、平台专属，而且实际收听时出现了断续，收益不抵代价。

## 声音延迟（2026-10-04）

Windows 本机（RTX 4090 主机，声卡 Minifuse 2，系统混音 44.1 kHz、周期固定 10 ms），用 `rcsdk_audio_latency` 测量：从咔哒声进入系统混音，到经 SDK 采集、编码、UDP 回环、解码、缓冲、播放后再次进入混音。扬声器本身的延迟不计。“改之前 / 改之后”指降声音延迟的那次改动（ROADMAP 的“声音延迟”一行）。

| 构建 | Opus | PCM | AAC |
| --- | --- | --- | --- |
| 改之前 | 88 ms | 67.5～85.5 ms | 未测 |
| 改之后 | 63.6～71.7 ms，CPU 约半载时不变，设备断档 0 次 | 64 ms | 155 ms |

- 同一次运行里每次咔哒的延迟都一样，不同运行之间相差最多 10 ms。原因是咔哒声每秒一次，正好落在 10 ms 混音周期的同一个位置；实际使用中这部分在 0～10 ms 之间，是系统周期本身带来的。
- 这台机器上剩下的延迟大多来自系统：采集 10 ms 周期（再加 0～10 ms 相位）、播放一个半周期 15 ms、混音与 44.1 kHz 重采样，加上观看端缓冲约 14 ms 和 Opus 的 2.5 ms。声卡支持更短的共享周期且混音格式为 48 kHz 时，SDK 会用低延迟共享模式，播放这一段还能再小。
- AAC 自身的编码延迟和 21 ms 的包长让它慢得多，所以默认是 Opus。

**Windows → Mac**（局域网 UDP，Mac 扬声器播放）：

- 观看端缓冲：改之前平时 20～40 ms，刚连上时约 100 ms，要 8 秒左右才降下来；改之后从第一秒起就是 14～20 ms。
- 60 秒 5982 个包，丢包 0。
- 各环节估算约 35～45 ms：Windows 采集 10～20 ms、编码和网络约 3.5 ms、缓冲 14～20 ms、Mac 输出 5.3 ms 加设备延迟。改之前的估算约 75～85 ms。端到端尚未用麦克风实测。
- 曾试过 Opus 固定 5 ms 一包：在 Windows 上每 10 ms 连发两个包，延迟没有变小，反而在局域网上有约 0.1% 的包丢失（30 秒丢 6 个）。所以改成包长跟随采集块。

## 关键发现

- **编码器跟不上目标码率时，必须降帧率**。
  - 内容太难压缩时，编码器的实际输出会超过目标码率。如果发送节流只按目标码率放行，数据就堆在分享端本机，网络看起来很空闲，控制器得不到拥塞信号。
  - 现在做了三件事：节流速率不低于编码器的实测输出；发送队列积压超过两帧时暂停采集；按目标码率的 1.3 倍设置编码预算，超出就跳过采集。
- **VideoToolbox 降码率时会主动丢帧**。之前这被当成了编码失败，现在按正常情况处理。
- **大关键帧要给足时间**。在慢速路径上，一个 130 KB 的关键帧光传输就要半秒。固定 200 ms 的放弃时间会让它永远补不齐，引发不断请求关键帧的恶性循环。放弃时间现在按帧大小和实测速率计算。

### Mac 发送端：低延迟编码器从未生效
VideoToolbox 不允许“固定 EncoderID”和“低延迟码率控制”同时使用（创建会话返回 -12902）。旧代码失败后悄悄去掉低延迟重试，所以 Mac 一直在用普通编码器，下文“Mac 4K 编码延迟”一节的独立测试数字其实没有在 SDK 里实现过。现在不固定编码器、只要求低延迟：4K HEVC 每帧从 33 ms 降到 18 ms。代价是这个实时编码器在提交调用里同步工作（独立测试：4K HEVC 提交调用平均阻塞 18.7 ms，最多 51.5 FPS；普通编码器阻塞 8 ms，105 FPS，但每帧延迟 84 ms），所以 SDK 在跟不上时自动切到普通编码器。

### Mac 采集：节拍、像素格式、缓冲数
- ScreenCaptureKit 的 `minimumFrameInterval` 恰好等于帧间隔时，稍早到的帧会让它多等一个刷新周期，60 FPS 实际只有 54。改为允许两倍速率交付，由 SDK 按截止时间取帧。
- VideoToolbox 自己把 BGRA 转成 YUV 太慢：4K120 HEVC 输入 BGRA 时延迟 91 ms，输入 NV12 时 18 ms。采集改为直接输出 NV12。
- `queueDepth` 为 3 时，编码器里压着 3 帧，再加最新帧，采集就没有空闲表面了，4K 采集只有约 78 FPS；改为 6 后可以超过 120。

### 输入后加速采集（实验）
被控端每执行一次远程输入，在接下来 100 ms 内按两倍帧率采集（实验时用环境变量 `RCSDK_INPUT_BOOST_MS=100`；现在是正式配置 `rcs_video_tuning_config.input_boost_ms`，CLI 的 `--input-boost-ms`）。测试窗口持续动画时，按键的效果要等下一个采集节拍，这正是加速省下的时间。Windows 被控、Mac 观看，交替测量：

| 配置 | 不加速 P50 / P95 | 加速 P50 / P95 | 平均帧率 |
| --- | ---: | ---: | ---: |
| 1080p60 HEVC | 37.4～38.7 / 45.5 ms | 33.7～34.0 / 39.6～42.6 ms | 60 → 69 |
| 1080p120 HEVC | 32.6～33.5 / 38.6～41.7 ms | **28.9 / 32.5 ms** | 120 → 127 |
| 4K120 HEVC | 36.8 / 40.0 ms | 33.6 / 38.3 ms | 120 → 127 |

结论：局域网 1080p120 加速后中位数低于 30 ms。同一配置在不同时间段测得的绝对值会差几毫秒（今天 1080p60 基线约 38 ms，之前约 32 ms），所以对比都用交替测量。真实使用中画面平时静止，静止时本来就立即采集，加速主要改善持续变化画面（视频、动画、拖动）下的操作手感。

### AV1（Windows 被控，Mac 观看）
NVENC AV1 编码，M4 Pro 硬件解码：1080p60 为 60.2 FPS、响应 40.0 / 48.1 ms；4K120 为 120.5 FPS、响应 35.8 / 42.5 ms，都零丢包，Mac 每帧解码约 2.2 ms。4K120 下比 HEVC 的 32.9 / 39.7 ms 高约 3 ms，在采样噪声范围附近。

### Intel 核显 QSV（Core Ultra 7 270K Plus）
用 SDK 编码器在核显设备上编码，每帧中位数 / P95：

| | 1080p | 1440p | 4K |
| --- | ---: | ---: | ---: |
| H.264 | 6.1 / 8.8 ms | 6.1 / 8.3 ms | 11.5 / 11.9 ms |
| HEVC | 6.6 / 8.8 ms | 6.1 / 8.0 ms | 11.5 / 15.0 ms |
| 对照：RTX 4090 NVENC HEVC | 3.2 / 4.1 ms | 4.6 / 5.9 ms | 5.1 / 6.5 ms |

- QSV 的 H.264 原来完全不能用：Intel 编码器在第一帧时用 `MF_E_TRANSFORM_STREAM_CHANGE` 重新给出输出类型，SDK 把它当成了错误。现在接受新类型，并等待下一次输出事件（立即重读会返回 `E_UNEXPECTED`）。
- 按 120 FPS 节拍提交时，QSV HEVC 在 1080p 和 1440p 都能达到 119.7 FPS，4K 只有 83.6 FPS（每帧 11.6 ms）。
- 试过“两帧重叠提交”（提交第 N 帧后再取第 N-1 帧的结果）：QSV 4K 反而降到 79 FPS、每帧 22 ms，NVENC H.264 4K 的每帧延迟从约 7 ms 翻倍到 13 ms。Media Foundation 编码器在这里并不能并行处理两帧，所以没有采用；4K120 超出这块核显的硬件能力。
- 这台混合显卡机器上，核显驱动的副屏在 DXGI 里也挂在 4090 名下，所以共享副屏时实际仍用 NVENC；SDK 按采集设备所在的显卡选编码器，只有显示器真正由核显输出时才会用 QSV。

### 4K 120 FPS：接收端的恢复螺旋
早期的实现在 4K 120 FPS 时，Mac 观看端只能解出 10～33 FPS，响应 190～250 ms，而分享端的码流完全正常（每秒 118 个包，没有超过 20 ms 的间隔）。原因是一个自我强化的循环：恢复时重置解码器会销毁 VideoToolbox 会话，下一个关键帧到来时重建会话约需 45 ms，这期间到达 5 个包，超过了 3 帧的队列上限，于是再次恢复。60 FPS 时 45 ms 只来 2.7 个包，所以一直没暴露。修复：重置时保留解码会话；接收队列改为以 80 ms 时间上限为准（帧数上限 3 → 16，只用于限制内存）。修复后 4K 120 FPS 稳定在 120 FPS。

### macOS 解码输出 NV12
VideoToolbox 输出 BGRA 时，YUV 到 RGB 的转换算在解码时间里。独立测试（M4 Pro，每帧中位数）：

| 解码 | 输出 BGRA | 输出 NV12 |
| --- | ---: | ---: |
| H.264 4K | 8.3 ms（关键帧 23 ms） | 5.1 ms（关键帧 8.8 ms） |
| HEVC 4K | 6.8 ms | 2.2 ms |
| H.264 1080p | 3.3 ms | 2.0 ms |
| HEVC 1080p | 2.7 ms | 1.2 ms |

8.3 ms 已经等于 120 FPS 的整个帧间隔。现在注册了 GPU 回调的宿主拿到 NV12，在着色器里转换；只要 CPU 图像的宿主仍然拿到 BGRA，因为 VideoToolbox 转换比 CPU 快。另外，在 Apple Silicon 上 HEVC 的 4K 解码比 H.264 快一倍多。

### Windows 4K 120 FPS 发送端各阶段
4K HEVC 120 FPS 时（当时的 `RCSDK_TRACE_MF`，现在是 CMake 选项 `RCSDK_TRACE`）：NVENC 编码 P50 5.4 ms / P95 6.2 ms，等待采集节拍 1.6 ms，其余各阶段都在 0.5 ms 以内，循环周期中位数 8.30 ms。同步流水线（采集后立即编码）已经足够，异步提交只能提高吞吐、不能降低延迟，只有在 4K 165 Hz 以上才需要。每帧新建纹理的开销在 P95 约 1.7 ms（颜色转换阶段），属于低优先级优化。

### Windows 发送端：等待精度决定帧率
早期的 Windows 发送端只有约 32 FPS。阶段计时显示每帧实际工作约 4 ms，但帧间隔等待和编码完成轮询都用了 `sleep_for(1ms)`。在 Windows 默认约 15.6 ms 的定时精度下，每次都睡满一个周期。改用高精度可等待定时器后（不修改进程全局定时精度），1080p 从 32 FPS 提高到 60 FPS。1080p / 1440p / 4K 每帧硬件编码分别约 2.9 / 5.6 / 9.2 ms。

### HDR 桌面上拖动窗口
在 FP16（HDR）桌面上，旧接口 `IDXGIOutput1::DuplicateOutput` 拖动窗口期间一直返回拖动前的画面，松开鼠标才更新；`IDXGIOutput5::DuplicateOutput1` 则实时更新。用不经过 SDK 的独立程序对照确认后，采集改为优先使用后者。

### 被控端显示器刷新率影响很大
同一台 Windows 机器从高刷屏换到 1080p / 60 Hz 屏后，Windows 被控响应中位数从约 42 ms 变成 71～80 ms。SDK 内部采集到编码完成的耗时没变（约 7 ms），增加的时间来自应用绘制、DWM 合成和桌面复制按 60 Hz 节拍等待。被控端用高刷显示器，远控手感会明显更好。

### Mac 4K 编码延迟来自硬件编码器
（更早的独立测试；SDK 当时实际没用上低延迟模式，见上文）独立 VideoToolbox 测试（实时模式，易压缩内容），编码延迟中位数如下：

| 编码器 | 1080p | 1440p | 4K |
| --- | ---: | ---: | ---: |
| H.264 低延迟码率控制（SDK 使用） | 5.4 ms | 8.6 ms | 16.9 ms |
| H.264 普通模式 | 5.8 ms | 11.8 ms | 67.5 ms |
| HEVC 低延迟码率控制 | 5.9 ms | 9.3 ms | 18.3 ms |
| AV1 | M4 Pro 无硬件编码器 | — | — |

关闭低延迟码率控制、优先速度、采集直接输出 NV12 这三项都试过，SDK 内 4K 编码 P95 只从 29 ms 降到 26.5 ms。结论：Mac 在 4K 下比 Windows 多出的十几毫秒是硬件编码器的特性；在 M4 Pro 上 HEVC 不比 H.264 快。
